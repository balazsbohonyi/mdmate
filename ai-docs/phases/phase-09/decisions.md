# Phase 9 decisions

Choices the plan left open, settled with the owner in a design session on 2026-11-13. Each one lists what was weighed.

## Order

- **Phase 9 runs before Phase 8.** Only paste needs a setting, and a built-in `assets` folder covers it. P8-T1 adds `images.pasteFolder` (ISC-330) and the paste code reads it then. Drop and resize have no dependency on Phase 8.

## Saving a resize

- **A resized `![alt](src)` becomes `<img src alt width>`.** Other formats were weighed: Obsidian's `![alt|300](src)` stays Markdown but only Obsidian reads the size, and Typora's `=300x` makes GitHub and VS Code treat the size as part of the URL. `<img>` renders in every viewer. **Cost:** a resized image is no longer pure Markdown. The owner accepted that; an unresized image is never rewritten (ISC-160).
- **mdmate therefore draws `<img>` tags (P9-T3).** Attributes honoured: `src`, `alt`, `title`, `width`, `height`. The address goes through the same allowlist as a Markdown image. Everything else, including `style` and `on*`, is ignored, and other HTML stays source. This is new attack surface; P10-T2 reviews it.
- **Width only.** The handle writes `width` and the browser scales the height, so the ratio holds. On an `<img>` that already has a `height`, the resize removes it (otherwise the image would distort); no other byte of the tag changes. MarkdownWeave writes both and lets the ratio break; this is deliberately different.

## Selecting

- **A click selects the image and keeps its source hidden.** Today a click puts the cursor at the start of the source. The new selection state shows an outline and the handle. Enter or an arrow key into the image shows the source for editing. Escape or a click elsewhere deselects. Delete or Backspace removes the whole image as one undo step. There is no keyboard resizing in v1.
- **Every loaded image gets a handle**, block or inline, local or `https`. Broken images and the loading placeholder get none. The range is 24 px to the editor content width; upscaling past the natural size is allowed, so a small image can be enlarged.

## Paste and drop

- **Folder and name.** `assets` next to the document, created on the first paste, so the relative link always stays inside the document's folder and passes the image allowlist. The name is `image-YYYYMMDD-HHMMSS.png` and a taken name gets `-2`, `-3`. Rejected: one folder at the workspace root (links climb with `../`, and a document in no workspace has no root) and a folder per document.
- **Drop links in place when it can, copies when it must.** A file inside the document's workspace folder is linked where it is. A file outside it is copied into `assets` and linked there, because an outside path would never load (ISC-180). Dropping outside the text still opens an image tab (ISC-201).
- **An untitled document gets a draft folder per document (P9-T5).** Pasted and copied images go to `drafts/<key>/assets/` in the app data folder, with the normal relative link, and the first Save As copies them next to the saved file and removes the folder. Closing the tab without saving removes the folder too (after "Don't Save", or at once when nothing changed), but quitting the app keeps it because the session restores the tab. There is no reopen-closed-tab feature in the ISA, so a closed untitled tab never needs its images back. Weighed and rejected: base64 in the text (the session snapshot writes every unsaved buffer, so a 2 MB screenshot would be rewritten each time, and the CSP would need a `data:` exception), a link form that only works in untitled tabs, asking to Save As on the first paste (an interruption), and saving to a default folder (writes somewhere the owner did not choose). What was built is in the P9-T5 section.
- **An undone paste leaves its file.** The text insert is one undo step; the image file stays on disk. mdmate never deletes the owner's files on its own, and deleting on undo would break a redo or an edited link.

## Still to check

- Settled in P9-T5: the untitled number is stored with the tab and brought back by `createUntitled(number)`, so it keys the same folder after a restart. `tests/documents/session.test.ts` covers the round trip; the real-window kill and restart (ISC-206) is the real check.

## P9-T1: Paste (2026-11-13)

**Where it was checked.** The real debug window (`target/debug/mdmate.exe`, display scale 150%, `devicePixelRatio` 1.5) against my own Vite server on port 1420, with `MDMATE_DATA_DIR` and `WEBVIEW2_USER_DATA_FOLDER` in temp folders, driven over the DevTools port with trusted key events (`Ctrl+V` with the `paste` editing command) and a clipboard filled from PowerShell (`SetImage`, `SetFileDropList`, which is what Explorer's Copy sets).

**The clipboard check (the open question in the plan).** A `paste` listener on the document read `clipboardData` for each case:

| On the clipboard | `types` | `files` | `text/plain`, `text/html` |
|---|---|---|---|
| A bitmap (a screenshot) | `Files` | one `File`: `image.png`, `image/png`, 1159 bytes (every pixel) | empty |
| One file copied in Explorer (png, jpg, gif) | `Files` | one `File` with the file's **real name**, **real type** and **exact bytes** (734, 907, 1008 bytes: the sizes on disk) | empty |
| Two files (png and jpg) | `Files` | two `File`s, in order | empty |
| A Markdown file | `Files` | one `File`: `note.md`, `text/markdown` | empty; pasting it inserted nothing |

So a file copy needs no path and no special route: **both cases are `clipboardData.files`**, and a pasted file is saved from its bytes like a screenshot. There is no path on the clipboard to refuse. Nothing but the `File`s comes through for a copied file, so the file's own folder is never learned.

**What follows from it.**

- **Text wins over a picture.** A paste with `text/plain` or `text/html` on it is an ordinary paste even when it carries an image file, because a copied spreadsheet range or web page puts a preview bitmap beside its text. Both measured cases have no text.
- **Four types are saved: PNG, JPEG, GIF, WebP.** Rust reads the type from the first bytes, not from the page's word for it, and the extension follows the type. A screenshot is `.png`, as the plan says; a copied photo is `.jpg`. The plan's name `image-YYYYMMDD-HHMMSS.png` named the screenshot case; saving JPEG bytes under `.png` would hand the owner a file that lies about its type. SVG is not saved (it is text, and not what a paste of a picture means); a copied `.md` or `.txt` is left to the paste that was always there.
- **The file keeps the stamp name, not its own name.** A copied `photo.jpg` becomes `image-20261113-174407.jpg`, the same naming as a screenshot. Several files at once get one link each, one under another, as one undo step; two files of one type in one second get `-2`.
- **The time comes from the page and is held to the shape `YYYYMMDD-HHMMSS`.** Rust has no clock for the owner's time zone, and the page does. Anything else (a `/`, `..`, a different length) is refused, so the stamp can never name a path.
- **The name is taken by creating the file.** `create_new(true)` in the `-2`, `-3` loop, so a name another paste or program took a moment ago is never opened for writing (ISC-329). A half-written file under a name this call created is removed.
- **Refused in Rust:** a document that cannot be edited, an `assets` that is a file, an `assets` that is a link or junction leading out of the document's folder (the image would not load, and the write would reach a place the document does not own), bytes that are not one of the four types, and more than 64 MB. A junction test creates a real junction with `mklink /J` on Windows and fails if it cannot.
- **Link text is written so it reads back.** A name with a space or parenthesis goes in angle brackets, and `%`, `#` and `?` are percent-escaped, because the address reader percent-decodes and treats `#` and `?` as a fragment and a query. A seeded test over 300 names with every awkward character goes through the real Markdown parser and the image allowlist and gets the same file back. It found `#` unescaped the first time it ran. (Today the name is always `assets/image-….png`; the folder becomes a setting in P8-T1 and may then hold such characters, and the drop in P9-T2 links files with any name.)
- **A document that was swapped out while the file was being saved gets no link.** The link goes in only if the view still shows the same tab; otherwise the notice says where the file went.
- **The notice is the status bar's `problem` line**, the same place other failed actions report to.
- **The folder is a constant `assets`** (`images::IMAGES_FOLDER`). P8-T1 will read `images.pasteFolder` at that one place (ISC-330).
- **The image protocol needs nothing new.** `assets` is below the document's folder, which `open_file` already granted recursively; a freshly created `assets` loaded without a restart.

**Evidence, real window.** A screenshot paste saved `image-20261113-174405.png` (1159 bytes, the bytes the clipboard check read) next to the document and inserted `![](assets/image-20261113-174405.png)` at the caret; the image drew at 240 x 140 CSS px natural size (360 x 210 on screen at 150%). A two-file Explorer-style paste saved `image-20261113-174407.jpg` (907 bytes) and `image-20261113-174407.png` (734 bytes), the sizes of the originals, and inserted two links; the jpg drew at 160 x 100 and the last link showed its source because the caret was at its end, which is the existing reveal rule.

## P9-T2: Drop (2026-11-13)

- **Rust decides, from its own drop record.** The page sends `image_drop(id, path, stamp)`; `path` must be one a native drop delivered (`DropRegistry::lookup`), and the file must be an image by extension. In place or copy is decided over there, so a hostile page cannot make the app copy a file or link a path by naming it.
- **In place or copy follows the page's own boundary.** The boundary is the innermost workspace folder that holds the document (the page's `rootOf` and the allowlist's climb limit use the same rule), or the document's own folder when it is in none. A file inside it is linked where it lies, relative to the document and with `../` where it has to climb. Any other file is copied. A document in no workspace therefore links only below its own folder.
- **The real file is what is checked.** Both paths are canonicalised first, so a drop through a link or junction that leads out of the workspace counts as outside and is copied; an in-place link there would never load (the asset protocol checks the real path) and would show a broken picture. A test makes a real junction.
- **A copy is named like a paste** (`image-YYYYMMDD-HHMMSS.<ext>`, `-2`, `-3`), the type read from the bytes, the same four types, the same 64 MB cap, and the original is left where it was. A picture of another type (SVG, BMP) links in place inside the workspace as before, but dropped from outside it is refused with "not a PNG, JPEG, GIF or WebP image", since there is no copy to make.
- **The link goes in at the drop point, not the caret.** The point is the one `host.onFileDrag` gives (physical pixels over `devicePixelRatio`, P0), turned into a position by `view.posAtCoords`. The caret ends after the link, as after a paste. Several pictures give one link each, one under another, as one edit. If the text got shorter while the files were handled, the point is held to the end of it.
- **Where the drop is not handled as a link it still opens a tab** (ISC-201): off the text; at a point with no position in the text; in a document that cannot be edited. An unsaved document copies the picture into its draft folder (P9-T5).
- **The drop tests use a stand-in for the position**, because jsdom has no layout: they assert the page point the drop asks about, and the position it is turned into is CodeMirror's.
- **Open:** the real-window drop (a real OLE drag from a second window over the app, one file inside the workspace and one outside, at the display's real scale of 150%) is not run yet, so ISC-156, ISC-328 and the task stay open. It runs with the other real-window checks at the end of the phase.

## P9-T3: Draw `<img>` tags (2026-11-13)

- **A small parser of its own** (`blocks/imageTag.ts`), not the Markdown tree's idea of a tag. The text must be exactly one `<img ...>` on one line with a non-empty `src`; of its attributes only `src`, `alt`, `title`, `width` and `height` are read, so a `style`, an `on*` handler, a `srcset`, a `class` or an `id` never reaches the page, because it is never read. The first of a repeated attribute wins, as in a browser. A tag that is anything else (no address, an unterminated quote, text after it, two tags, a line break inside) is not an image and stays source.
- **The address goes through the Markdown image's allowlist, after character references are read.** `&amp;`, `&lt;`, `&gt;`, `&quot;`, `&apos;` and numeric references are decoded (a reference to a control character stays as written); decoding comes first, so `&#46;&#46;/` is `../` and is refused like it. Nothing else about the address differs from `![]()`: relative inside the folder or the workspace folder, or https.
- **Sizes are whole pixels**, `300` or `300px`, 1 to 99999; `50%`, `30.5`, `1e3`, `0` and the like are ignored. One given side makes the other follow the picture's proportions; both given make that exact box (`object-fit: fill`, as a browser draws it, where Markdown images use `contain`). The frame's `max-width: 100%` still keeps a wide one inside the editor.
- **Where it draws** is where a Markdown image draws: a tag alone on its line is a block (the parser calls it an HTML block when nothing precedes it, and a paragraph line otherwise; both are read), a tag inside text is inline, and inside a table, a list, a quote or a code span it is text. An `<img>` inside other inline HTML (`<a href><img></a>`, `<picture>`) draws too, and the tags around it stay source, so a linked badge shows its picture. A tag in an HTML block with other lines after it (no blank line) is part of that block and stays source.
- **hostile.md gained six `<img>` tags** (an `http` and a `file` address, a drive letter, a UNC path, one with `style`, `onerror` and `onload`, one with `srcset`), written in its generator \`scripts/fixtures.mjs\` because a test keeps the committed fixture equal to what the generator makes. The existing "only https loads" test now reads the Markdown images, and the new tests read the tags: the only addresses a hostile tag gets are its own relative `x`, `x.png` and `y.png`, which the allowlist allows for any image.
- **No new network or script surface in the page**: the widget sets `alt`, `title` and `src` through DOM properties, never through `innerHTML`; the label and title are text.
- **Not seen in the real window yet**: the picture drawn from a tag at its width. The jsdom tests assert the frame's size and ratio; the look runs in the end-of-phase real-window pass with the resize.

## P9-T4: Select, resize and delete (2026-11-13)

- **A click sets a flag; the caret stays where it was.** The selected image is a per-view `StateField` (`blocks/imageSelect.ts`) holding its source range, set by an effect from the widget's mousedown. The old behaviour (a click puts the caret at the start of the source) is gone; Enter or an arrow key does that now. Anything that moves the selection, changes the text, or presses elsewhere drops the flag, except a transaction that sets it itself (a resize keeps the image selected for another drag). The block layer's rule that a block is drawn only while no selection touches it is unchanged: no exemption was needed, because a drawn image is never touched by the caret, and a caret that moves onto it clears the flag in the same transaction.
- **Keys while an image is selected** take a high-precedence binding: Delete and Backspace remove the source (one history step, isolated so a deletion made just before is not joined to it); Escape drops the flag; Enter and ArrowDown/ArrowRight put the caret at the start or end of the source, which shows it. Typing and paste only drop the flag, since the caret they would act on is somewhere else. Cut and copy take the source. The caret and its layer are hidden while an image is selected.
- **The handle exists only after the picture has loaded**, built in the load step, so a broken image and the placeholder never have one. A drag changes the frame's style only; the text is written once on release (`commitResize`), so a drag is a single undo step, and a pointer cancel or a redraw of the widget mid-drag restores the frame. The start width is the frame's rendered width, the range is 24 px to the text column's width, and each move asks CodeMirror to measure again because the frame's height changes.
- **`<img>` edits are attribute-level, not a rewrite.** The tag scan records where each attribute sits; a resize sets the first `width` (keeping its quotes, or writing `width="N"` for an unquoted or bare one), adds ` width="N"` after the last other attribute when there is none, and removes every `height` with the gap before it. A test that removes `width` and `height` from the tag before and after by an independent rule checks that the rest is byte-equal on 3000 generated tags.
- **A Markdown image is rewritten whole, or not at all.** The tag is built from the address (as written, angle brackets taken off as the allowlist does), the label and the title, escaped for an attribute, with a multi-line label or title collapsed to one line (the tag reader accepts one line only). The result is parsed back; if the address, label, title or width differ, nothing is written.
- **One stated exception to ISC-159.** `<img ...>` alone on a line starts an HTML block that runs to the next blank line (checked with a parser probe: `<img>` plus a caption line is one `HTMLBlock`). A resized Markdown image that is the first line of a paragraph with more lines after it would therefore turn those lines into raw HTML in every other viewer and stop mdmate drawing a picture written on the next line. In exactly that case the resize ends the tag with one line break (the document's own). It is not needed after a line of text in the same paragraph, where the tag is inline. The owner can drop the rule by removing `joinsNext` in `blocks/imageEdit.ts`; ISC-159 now names the exception.
- **A tag's trailing spaces** (a line `<img ...>  `) used to make the parser's HTML block longer than the tag, so it was no longer "alone on its line" and drew inline; the item is now the tag alone.
- **Not seen in the real window yet:** the outline and handle look, the real drag and its measure cycle, the pointer capture, and the click-to-select and Escape behaviour (ISC-157, ISC-322). They run in the end-of-phase real-window pass.

## P9-T5: Images in untitled documents (2026-11-13)

- **One Rust module owns every draft folder (`drafts.rs`).** The page sends the number in the tab's name (`Untitled-3` gives 3) and never a path; Rust builds `<data folder>/drafts/<n>` from it. Numbers must be 1 or more and two open untitled documents cannot share one (the first one to ask wins; the second is refused with `invalid`), because the number names the folder.
- **Nothing is made or deleted until it must be.** The folder appears with the first pasted or dropped image, never when the tab opens, so opening a tab can never touch a folder that a restored tab owns. A restored tab brings its number back and finds its images.
- **Deleting is guarded because it deletes.** Every path is built from a checked number. A folder that is a link or junction is never entered or removed (`symlink_metadata`), a `drafts` folder that is itself a link is not used at all, and the start-up sweep touches only direct children whose names are plain numbers (`007`, `-1`, `notes` and files are left alone). Closing a tab removes its draft best-effort, off the command's thread; a folder that will not go is left for the next sweep, and a failure never fails the close.
- **The sweep runs only after a restore with no notice.** A damaged or partly restored session may still name a tab that did not come back, and its draft is the only copy of its images. A first start has no session and sweeps nothing. The page passes no numbers; Rust keeps those of every untitled document that is open.
- **Recovered text keeps its images.** When a session's untitled tab cannot come back (its record is damaged, or the layout lost it), its text goes to a recovery file and the document is closed, which removes its draft folder. A test found that this lost the images. `session_recover` now takes the untitled number; `SessionStore::recover_with_images` copies the images the text links to into `recovered/assets/` (a taken name gets `-2` and its link is updated) before the text is written, so the recovered file's `assets/…` links resolve beside it. If the pictures cannot be copied the text is still recovered as it is: text outranks pictures. `session.test.ts` checks the images are beside the recovered file; the Rust tests are `draft_images_recovered_*`.
- **Dropped pictures are always copied.** An untitled document has no workspace folder, so there is no "in place": every dropped picture goes into the draft folder, whatever it is, and its link is the plain `assets/…` one.
- **The asset scope grows one draft at a time.** Rust grants the draft folder (as the page was told it and as it really is) when its first image is saved, and again when a restored tab's folder exists; never the `drafts` folder. The scope only grows while the app runs. What keeps a tab off another tab's draft is the page's address allowlist, since a link that leaves its own folder is refused (`imageAddress.test.ts`).
- **First Save As: copy what the text uses, then write, then remove.** Only images the text links to as `assets/<name>` (after a character that is not part of a path, or after `./`; not `../assets/` and not `myassets/`) are copied, with `create_new`, so nothing is overwritten and a taken name gets `-2`, `-3`. The links of renamed images are rewritten in Rust before the file is written, in one pass so a name that is another's new name is not renamed twice. If the write fails, the copies are removed and the draft stays. A pasted-then-undone image that the text no longer links to stays behind and goes with the draft.
- **The page does the same rename on what it holds.** Rust returns the renames. The page applies them to the document's text as a change history does not record (undo never brings back a name the disk no longer has) and to the baseline it compares against, so the document does not look edited. The rule that finds links is one function in each language, checked against one set of cases (`tests/data/draft-links.json`) that both run.
- **A Save As target inside the drafts folder is refused**, since the file would go with its draft.
- **Not seen in the real window yet:** the Tauri commands (`document_new_untitled`, `drafts_sweep`, `close_document`, `session_recover`), the asset scope grant (does the picture draw), Save As with a real dialog, and a real kill and restart. The real-window pass must also check: after a Save As that renamed an image, switch tabs and back so the widgets rebuild, and every picture (the `-2` one included) draws from the new folder and none points at the removed draft; and after a kill and restart with an untitled tab that has an image, the image draws, which proves the scope is granted again for a restored tab.
- **For the owner to decide: ISC-333's wording.** It says the asset protocol is granted a draft folder "only for the untitled tab that owns it". Tauri's asset scope is app-wide and only grows, so Rust cannot grant per tab; what separates tabs is the page's address allowlist (a link that leaves its own folder never loads; `imageAddress.test.ts`), and Rust grants one draft folder at a time, never the `drafts` folder. A reword that says that is proposed; ISC-333 stays open until it is accepted and the real-window check has run.
