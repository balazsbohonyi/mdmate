# Phase 4: what was not tested, and how to test it later

Everything below was skipped on purpose or could not be done in the Phase 4 runs. Each entry says why, and how to check it when there is time. The decisions behind them are in [decisions.md](decisions.md).

| # | Gap | Why it was skipped | How to test it |
|---|---|---|---|
| 1 | The parse frontier landing exactly on the end of a table | A mutation of the removal filter survived: no test can put the frontier there on demand. | Open a very large document with many tables in the real app, scroll to the bottom while parsing catches up, and check that no table is missing or drawn twice. |
| 2 | Tables wider than the pane | The wrapper scrolls sideways, but no check looked at a wide table. | Open a table with ten long columns in a narrow pane and scroll it sideways. |
| 3 | The light theme | As in Phase 3, every visual check ran in the dark theme. | Switch to the light theme and look at the table header, borders and inline code. |
| 4 | A relative image path that leaves the document's folder (`../images/a.png`) | Refused on purpose: allowing it means granting the parent folder, which ISC-181 rules out. | Decide whether a workspace root (a later phase) should widen where an image may come from, then open a document in a subfolder of a workspace. |
| 5 | Scrolling with a real wheel or trackpad over images | The scroll check moves `scrollTop` in steps; no trusted wheel events were sent. | Send trusted wheel events over the DevTools port in the real window and watch the top line. |
| 6 | Images in a list item, a quote or a table cell | Left as Markdown on purpose: a block replacement there would lose the line prefix. | Open a README with images in list items and decide if that needs a block layer that keeps prefixes. |
| 7 | Animated GIFs, very large images, images that take seconds to load | Only PNG and SVG of at most 880 px were tried. | Open a document with a 20 MB PNG and an animated GIF and watch memory and scrolling. |
| 8 | Images in the light theme | Every visual check ran in the dark theme. | Switch theme and look at the placeholder border and label colours. |
| 9 | A document at the root of a disk (`C:/x.md`) | Rust refuses to grant a whole disk, so its images show placeholders; checked in a unit test only. | Open a document at the root of a drive and confirm the placeholder. |
| 10 | The asset scope only grows | Tauri has no way to take a folder back out. | Nothing to test; revisit if Tauri adds revocation. |
| 11 | Scroll stability beyond the lab walk | ISC-72 passes 6 of 6 runs, but only on one lab document, in 60 px steps set through `scrollTop`, with local images. | Try trusted wheel events and a trackpad over the lab document, scrolling down into images not yet seen, and an `https` image that loads late. |
| 12 | The 12 px anchor point | It is a constant copied from CodeMirror 6.43.15 (`scrollAnchorAt`); the check would notice a change, but nothing else watches it. | After a CodeMirror update, rerun `pnpm perf scroll-stability`. |
| 13 | Frontmatter that opens a construct the parser carries past its closing line | The tree still sees the YAML as Markdown, so an unclosed code fence inside the block would swallow the text after it. | Open a file whose frontmatter holds a line of three backticks and look at the body. |
| 14 | Frontmatter edge cases: a BOM, a block of more than 200 lines, `---` closed by `...` in the real window | A BOM is a separate flag on the opened file and was not tried here; the limit and `...` are covered by unit tests only. | Open real Jekyll, Hugo and Obsidian files and look at the pill. |
| 15 | Checkboxes by keyboard | The box has `tabindex=-1`: it cannot be reached with Tab, and nothing toggles a task from the keyboard. | Decide if a shortcut that toggles the task on the caret line is wanted (Phase 5 or later). |
| 16 | Checkboxes in the light theme and under a screen reader | Only the dark theme was looked at, and the native box has no label. | Switch theme; run a screen reader over a task list. |
| 17 | A press while the file changes on disk | Presses go through the document like typing, so the external-change path applies; not exercised together. | Press a box while another program saves the file. |
| 18 | Pressing the frontmatter pill in the real window | Only the jsdom test presses it (the caret goes to the start and the YAML shows); the real window was checked by moving the caret in and out. | Press the pill with a trusted mouse over the DevTools port. |
| 19 | Light theme token colors by eye | The computed colors are right (keyword `oklch(0.48 0.15 310)`, string `oklch(0.46 0.11 145)`, number `oklch(0.5 0.13 50)`), but the DOM-render screenshot washed them out and the real window was only looked at in the dark theme. | Switch the real window to the light theme and look at a fixture with ts, python and rust blocks. |
| 20 | Contrast of the token colors | No contrast ratio was measured for either theme. | Measure each `--syntax-*` color against `--background` and `--syntax-code-background`. |
| 21 | A cold first load of a language | The block is plain until its parser arrives; on a cold disk or a slow machine that may be visibly longer than the half second seen here. | Open a document with a Rust block in a fresh profile and time the change. |
| 22 | Many blocks, long blocks, big documents | A document with hundreds of fenced blocks in many languages was not tried; the perf scenarios run after T4 use their own documents. | Open a document with 300 blocks in 10 languages and type in one. |
| 23 | Fence words beyond the common ones | Only ts, js, python, py, rust, css, json, sh, go, html and a few aliases were opened; the list has about 100 and a few have no extension match (a word that is neither a name, an alias nor an extension is plain). | Try `jsonc`, `tsx`, `vue`, `dockerfile`, `toml`, `ps1`, `bat`. |
| 24 | `pnpm check` does not inspect the build | It checks the bundle only if `dist/` has source maps, otherwise it prints a note and passes. A regression that adds a parser to the entry is caught only on a run with `--dist` (or after `vite build --sourcemap`). | Decide whether `pnpm build` should always write source maps (or a separate `check:bundle` script should build to a temp folder), then wire it into the release steps. |
| 25 | Raw mode in the light theme with the new highlight style | `tokenHighlight` replaced `defaultHighlightStyle` there too; only the dark theme was looked at. | Press Ctrl+E in the light theme on a document with headings, links, quotes and code. |
| 26 | Perf scenario changes | decorations-scale and reveal pass only with the settle step and the fixed 5000-character scan (e564f1c, owner approved). typing-5mb is dropped from the named list and not run. | Nothing, unless you want the scenarios changed back. |
| 27 | The jump after a long parse | After `forceParsing` the caret line was 198,810 px away for about a frame in a 10 MB file. Seen again in the 1 MB tables document with the old widget too: a view parked at about 13,400 px right after open moves about 3,000 px when the parse finishes, 170 to 270 ms later. Not looked at in the 3 MiB range or with the background parse instead of `forceParsing`, and I have not checked whether a person scrolling would see it. | Scroll to the end of a 3 MB file in the real window and record where the view sits frame by frame. |
| 28 | Tab-switch at T2 and T3 | Not measured and no longer needed: the cause was profiled instead (one big table) and fixed in 4a1383d. | Nothing. |
| 29 | A tab opened scrolled deep into a big table | The rows after the first 50 are a blank spacer until the fill: 2 to 3 frames, 52 to 80 ms in six samples (debug app, 9000 px into a 170-row table). With the idle-only fill it was 1 to 2 frames, 39 to 45 ms. The write-phase swap costs this to avoid a line moving up to 107 px. | Open a tab saved deep inside a table of 100 or more rows and look for a flicker. |
| 30 | The fill as a long task | The frame that swaps in the rest of a big table takes 45 to 64 ms against 17 ms (debug app, dev JavaScript; release not measured). The old widget's whole-table frame took 99 to 148 ms. Keys typed in that frame wait for it; typing is not measured with it. | Switch to the tables-heavy fixture and type at once; read the key times in the release build. |
| 31 | Far scrolls into unmeasured tables | Scrolling up step by step through the tables document gave a few frames of thousands of px of movement with both widgets (3 with the old, 2 with the new): rows are about 78 px against the 33 px estimate, so CodeMirror corrects big heights as tables come into view. That test cannot tell a small difference between the widgets. | Make `ROW_HEIGHT` closer to the real height, or measure a sample, if the jump bothers you. |
| 32 | The idle path in the unit tests | The deferred fill uses `requestIdleCallback` where it exists and `setTimeout` otherwise. jsdom has no idle callbacks and no layout, so the tests cover the `setTimeout` path and a click at a stubbed position. The idle path is what the real window ran. | Nothing. |
| 33 | Scroll stability with a big table | The `scroll-stability` scenario has no table over 50 rows. The fill was checked only in the debug app: the line under a big table, parked at the top, 14 runs with the write-phase swap, settled where the old widget leaves it in 13 and stayed 18 px off in one. Not a release-build scenario and not a gate. | Add a table document to `scroll-stability` if you want this gated. |
| 34 | Several big tables filling at once, in the real window | The shared-key bug (only the last table of several filled) is covered by a unit test with a stand-in view. A walk down `tables-heavy-1mb.md` in the debug app (28 stops, 29 big tables seen after their fill) found no spacer left, with the buggy version too, so I never saw it happen for real. | Nothing, unless you want a release-build check that no spacer is left after a long scroll. |
