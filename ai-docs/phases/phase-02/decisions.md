# Phase 2 decisions

Deviations from the plan and choices it left open. Numbers carry the OS they came from.

## Checking the UI (all of Phase 2)

- **Same as Phase 1.** Browser checks use Claude in Chrome on `pnpm dev`; real-window checks use `pnpm tauri dev` with real OS input and screenshots over the WebView2 DevTools port (see "Checking the UI" in the Phase 1 decisions).
- **Rust tests never touch real files.** Fixtures are read from the repo and copied into temp folders before anything is saved.

## P2-T1

- **Rust owns the whole byte transform; the page owns the text.** `open_file` returns one raw frame: a JSON header, the line-ending exceptions as little-endian `u32` pairs, and the text as UTF-8 with `\n` as its only break (BOM stripped, UTF-16 transcoded). `save_file` takes the same frame back. Rust joins the endings, re-encodes with the original BOM and encoding, and writes. This was the advisor's call: the ISC-1 and ISC-2 probes are Rust tests, so the code that touches bytes has to be Rust. The layout is in the header comment of `src-tauri/src/fs/frame.rs`; the page's half (`src/platform/frame.ts`) arrives in T2 and must change with it.
- **Only the breaks that differ from the dominant ending are sent.** A plain CRLF or LF file carries no list; a mixed one carries a short one. The dominant ending is the most common one, the first to appear wins a tie, and `\n` when the file has no breaks. The pairs start on a 4-byte boundary (header padded with zeros) so the page can read them as a `Uint32Array` without copying.
- **A round-trip guard runs at every open.** If decoding, splitting, joining and encoding again would not give the same bytes, the document opens read-only (`not-round-trippable`) and a save is refused. This makes ISC-1 hold for any file, not only the fixtures. With a mutated `join` the fixture test failed and the random-bytes test still passed, because the guard turned the damaged files read-only: that is the guard doing its job.
- **Supported encodings: UTF-8 (with or without BOM), UTF-16 LE and BE (with BOM).** Everything else opens read-only as `unsupported-encoding` with every byte shown as the Latin-1 character of the same number, so nothing is dropped from view. UTF-16 without a BOM is not detected: it would be guessed, and a wrong guess can change bytes. Invalid UTF-16 (a lone surrogate, an odd byte count) is unsupported, since it could not be written back.
- **Atomic save.** A temp file next to the target (`.name.mdmate-<pid>-<n>.tmp`) is written, flushed with `sync_all`, given the original's permissions, then renamed over the target. A failure anywhere removes the temp file and leaves the original as it was. The test hook is a closure called just before the rename (`write_atomic_with`), so ISC-40's failure is injected without any global state. The target is the resolved path, so a symlink stays a symlink.
- **Path policy: the page may only touch files Rust saw the user choose, or files inside an open workspace folder.** `read_file` and `open_file` check every path (`src-tauri/src/access.rs`) against two sets: single files granted one by one, and workspace roots. Paths are compared resolved (symlinks and `..` followed), so a link inside a root cannot lead out of it, and case-folded where the OS ignores case. Network (UNC) paths are refused. Only Rust's own events grant: the open dialog today, a restored session in T6, a folder picker and launch arguments later. The page has no command that grants, because a page that can grant itself access has no limit at all. Phase 2 grants single files only; roots wait for Phase 6, so `grant_root` is built and tested but unused in a normal build (perf builds use it for the fixtures folder).
- **The page saves by a document id, never by a path.** Rust issues the id on `open_file` and remembers the resolved path, the format and the last known hash. Opening the same file again, however spelled, returns the same id (this is also what ISC-174 rests on). A save for an unknown id, a closed one or a read-only one is refused. The id travels in the `x-document-id` header, a plain number, because header values must be ASCII and file names are not.
- **Open dialog: `rfd` directly, not `tauri-plugin-dialog`.** The plugin pulls `tauri-plugin-fs` into the build graph (`cargo tree -i tauri-plugin-fs` shows it under the dialog plugin). It would never be initialized and the page would have no `fs:` permission, but ISC-21 says the crate is absent, and "absent" is the safer reading. `rfd` is what the plugin wraps, with the same feature set. The dialog runs in `spawn_blocking`, parented to the window, and the page gets no `dialog:` permission.
- **Case folding sits behind the platform trait** (`Platform::paths_ignore_case`: true on Windows and macOS, false on Linux), so `check-arch` keeps `target_os` inside `platform/`. macOS volumes can be case-sensitive; the default is assumed.
- **Mutation proofs (the code broken on purpose, then restored):**
  - `join` ignoring the exceptions: `roundtrip_unedited_gives_back_every_byte_of_every_fixture` and `roundtrip_unedited_through_the_file_system_keeps_the_hash` fail.
  - `encode` dropping the UTF-8 BOM: the same two fail.
  - Saving straight to the target instead of through a temp file: `atomic_save_failure_before_the_rename_leaves_the_original_intact` and `atomic_save_failure_leaves_a_missing_file_missing` fail.
  - The restored code passes all 67 Rust tests.
- **ISC-37 is not closed here.** Its probe passes (`save_writes_edits_in_every_supported_encoding`), but the claim says Ctrl+S, and the shortcut does not exist until the Save command is wired in T2. It closes there, as ISC-169 moved from T1 to T3 in Phase 0.
- **ISC-1 closes on the Rust probe.** The page half (the frame codec and the store passing text through unchanged) is covered by a web test in T2. If that finds a gap, ISC-1 reopens.

## P2-T2

- **The page keeps documents in a plain map and tells the chrome through a small reactive record.** `src/documents/store.ts` holds one `Document` per open file (editor state, saved snapshot, disk hash). Vue reads only `DocMeta` (name, path, dirty, read-only reason, last save error) from a `shallowReactive` map, so editor objects never enter Vue's reactivity (rule one). A document lives until its last tab closes, then the host is told with `close_document`.
- **Tabs are a `kind` union, and `TabInfo` now carries `kind`, `title` and `dirty`.** `TabRecord` has one member today (`markdown`, with a `docId`); Phase 6 adds text and image tabs as new members. The titles map from Phase 1 is gone: a tab's title is its document's file name. `workbench/store.ts` is still the only place that owns layout and tab records, and `splitTree.ts` is untouched.
- **A split opens a second tab on the same document.** This replaces the Phase 1 stand-in that copied the title. **Until P2-T3 lands, two panes on one document do not stay in step**: each view holds the state it was given, so typing in one is not shown in the other, and the last view parked wins. T3 replaces this with the master and follower views. The two tasks were built back to back for this reason, and nothing should be released between them.
- **Closing the last tab of a document with unsaved edits asks first, in a banner inside the pane, not a modal.** Save, Don't save and Cancel. Save that fails keeps the tab open and shows the reason. Closing a tab while another tab shows the same document asks nothing, because the edits stay visible there. Closing the app never asks (ISC-49, P2-T6): hot exit keeps the edits instead.
- **Ctrl+S is taken from the page whether or not it saves.** Save is disabled while the focused document is clean or read-only (the menu greys it), but the key handler still swallows the press, so the browser's own Save As never opens. A web test presses the key on a clean and on an edited document.
- **Saves run one at a time per document, and an edit made during a save stays unsaved.** The save sends a snapshot (text and endings at that moment). When it lands, only that snapshot is marked saved; the document is clean only if it still equals it. A test holds the host's write open and types in the meantime.
- **Dirty means "different from what is on disk", not "edited".** A document is compared (text and endings) with its last saved snapshot, so undoing back to the saved text clears the marker.
- **Opening works with no folder open.** The store has no notion of a root: `openPath` asks the host, and Rust decides by its path policy whether the file was chosen by the user. That is what ISC-98 rests on, with `access.rs` covering the Rust side (a granted loose file is readable, its neighbour is not). Opening a file that is already open, in any spelling of its path, focuses its tab, in the pane that has it.
- **Open dialog from the page: `pick_files` returns the chosen paths, then `open_file` for each.** The grant happens inside `pick_files`, in Rust, before the page learns the path. The page has no command that grants access, so a path it invents is refused. In the real app this was checked directly: with the DevTools port, `open_file` and `read_file` on a real file nobody chose both return `not-allowed`.
- **The mock host has in-memory files** (`createMockHost`, `src/platform/mockFiles.ts`), split into text and endings the way `eol.rs` does, with Windows-like case-insensitive paths, ids that stay the same for the same file, and a read-only file kind. `pnpm dev` ships five demo files (LF, CRLF and mixed) and Ctrl+O opens the next one in turn, since a browser tab has no dialog. Tests hand the app their own host with `setHost`.
- **The page half of the frame has a byte-for-byte pin shared with Rust.** `the_bytes_match_what_the_page_expects` (Rust) and `reads the bytes Rust writes for the same document` (web) build or read the same 59 bytes. If either side changes the layout, one of the two fails.
- **The line-ending field exists now, with its core job.** Save needs it, so `src/editor/lineEndings.ts` is real in T2: it follows each edit, shifts later breaks' indices, and gives a new break the ending of the line it was typed on. T4 still owns the two gaps from the spike (undo restoring a deleted break's old ending, and moved text keeping its endings) and the property tests.
- **A small fix found while checking the real window:** the `not-allowed` message carried Windows' verbatim prefix (`\\?\C:\...`), and the page shows that text. It now goes through `display_path`, and a test pins it.
- **No new crates and no new Tauri permissions in this task.**
- **Mutation proofs (the code broken on purpose, then restored):**
  - The frame ignoring its 4-byte padding: both frame tests fail.
  - The endings field not shifting later breaks after an edit: `keeps later line breaks with their own endings when lines are added or removed before them` fails.
  - Save sending no endings: that test and `keeps the line endings the file had` fail.
  - The restored code passes all 34 tests in `tests/platform` and `tests/documents`.
- **Checked in the browser (Claude in Chrome on `pnpm dev`):** the app starts with no tabs. Ctrl+O opens README.md and notes.md in tabs, with content and the path in the status bar. Typing shows the dirty dot, and Ctrl+S clears it and writes the file (the original text plus what was typed). A mixed-endings file (LF, CRLF and CR) saved with one character added at the start comes back as `>LF line`, a CRLF, `old Mac line`, a lone CR, `last line`, byte for byte. Closing an edited tab shows the banner, and Don't save closes it and leaves the file alone. No console errors.
- **Not checked in the real window: the native Open dialog, and a save through the real Rust path.** The desktop was locked for this whole session (`LogonUI.exe` running, and a screenshot showed the lock screen), so real OS input was not possible and I sent no more keys after one Ctrl+O that reached the lock screen. What was checked there: the app starts as the Tauri host, and the path policy refuses a file nobody chose. The dialog and a real save are covered by Rust tests and by the browser run, not by a human-style run in the window, and I will repeat them in the real window with P2-T6's checks.
- **How the real app was started this time.** The repo's Vite server was already listening on port 1420 (not started by me), so `pnpm tauri dev` would have collided with it. The app was run with `cargo run` from `src-tauri` against that server, with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222`, and stopped afterwards. The Vite server was left running.

## P2-T3

- **One headless master per document, one follower per tab.** The master (`Document.master`) is an `EditorState` that no view ever shows. It owns the text, the undo history and the line endings. A tab's state is a `Follower`: no history of its own, the default keys, the Markdown parser, and a `followerSync` extension that sends what the user does to the master. This is the structure the architecture doc already described; T2's stand-in (every view showing the master state directly) is gone, and so is the hazard noted in T2.
- **An edit goes follower, master, every other follower.** The follower's transactions reach the master through an update listener (the master takes the changes, the resulting caret, and the annotations history reads: what kind of edit it was, when it happened, whether it counts for undo, and whether it ends a group). The master's change set then goes to every other follower. A transaction that the sync itself made carries `syncAnnotation` and is never sent back. This is what lets quick typing in either pane undo as one step, as in a view with its own history.
- **A follower no view shows only notes the change.** Typing in one pane must not make every parked tab parse. A parked follower keeps one composed `ChangeSet` and applies it when its state is next read (when its tab is shown). A test counts the calls: twenty edits elsewhere make one `update` when the parked follower is read.
- **Undo and redo run against the master, and the result is shown everywhere.** Both keys call the document, not CodeMirror's history on the view. The master's step goes to every follower; the one that asked also gets the caret the undone edit was made from. `Mod-z`, `Mod-y`, `Mod-Shift-z` on Mac and `Ctrl-Shift-z` on Linux are the same keys CodeMirror's history keymap uses. Selection undo (`Mod-u`) is not bound: there is no selection history on followers, and nothing asks for it.
- **The master gets the caret an edit was made from.** History stores the selection from before an edit, and the master's caret is whatever follower moved last. So before each edit the master is given the editing follower's caret, as a step that does not count for undo. A test moves another follower's caret in between and still gets the right caret back after undo.
- **Closing a follower keeps the history.** The history is on the master, so closing a tab (or all of a document's tabs and opening it again) loses nothing while the document is open. It ends when the last tab closes, as the dirty-close banner already warns.
- **A tab's view is shared by the pane and swapped with `setState`.** `EditorHost.vue` holds one view per pane. A switch parks the follower it leaves (taking its state back from the view) and shows the next with `view.setState`. A new follower starts with the master's text and caret, so a split opens at the same place.
- **`createState` stays for standalone editors** (the P0 spike tests); documents use `createMasterState` and `createFollowerState` in `src/editor/create.ts`. `Document` takes `parser` and `extensions` options, which is where the size cutoff (T7) and live preview (Phase 3) plug in.
- **ISC-6's scenario now measures the real path.** `pnpm perf tab-switch` opens both 1 MB files through Rust (`openFile`), makes a `Document` and a follower for each, and switches with `Follower.show`. Every other switch lands on a tab whose document was edited in another pane meanwhile, so it also applies a pending change; those switches count toward the p95 like any other. The throwaway decorations stay on, so the numbers are comparable with the Phase 0 baseline until Phase 3 replaces them.
- **Mutation proofs (the code broken on purpose, then restored):**
  - Edits not sent to the other followers: at least eight tests fail (the output was cut at eight), including the two-follower sync, undo from the other follower and the random run.
  - Undo reaching only the follower that asked: four fail.
  - Closing a follower resetting the history: three fail, among them the two ISC-43 tests.
  - The master keeping the wrong caret before an edit: `records the caret an edit was made from, even if another follower moved it since` fails.
  - Parked followers dropping their pending changes: at least eight fail, the same ones.
  - The restored code passes all 39 tests in `tests/documents`.
- **The random test.** 150 seeded runs of 40 steps each mix typing, deletes, caret moves, undo, redo, opening and closing followers over 1 to 3 followers, and after every step all followers equal the master. At the end of each run, undoing everything gives back the opened text and redoing everything gives back the top of the history.
- **ISC-6 result (`pnpm perf tab-switch`, release build, Windows 11, Ryzen 7 8840HS, WebView2 157, five runs after two warm-ups):** switch p95 11.2 ms (runs from 9.4 to 11.7 ms) against 50 ms; median 7.7 ms; worst single switch 14.2 ms (runs 12.1 to 19.9). Plain switches have a median of 8.2 ms and switches that also apply a change made in another pane 6.9 ms; the synchronous part of a switch is 1.1 ms. The page was visible and focused and frames came every 17.7 ms, so the locked desktop did not throttle it. **The harness marks the run "repeatable: NO"** (one run sits 1.8 ms under the median, outside its 10% or 1 ms rule) and warns the CPU was under 85% idle before three runs. I did not rerun to get a clean pass: every run is under 12 ms, a quarter of the target, so more samples would not change the verdict.
- **Checked in the browser (Claude in Chrome on `pnpm dev`):** after Ctrl+O and a split to the right, both panes show the file. Text typed in the right pane appears in the left one, and both tabs get the dirty dot. Ctrl+Z pressed in the left pane reverts what was typed in the right, in both, and clears the dots. After typing in the right pane and closing its tab (no prompt, since the left tab still shows the file), Ctrl+Z in the left pane reverts that edit and Ctrl+Y brings it back. With two tabs in one pane, switching swaps the content and keeps each tab's edits, with one editor view for the pane. No console errors.
- **Still not checked in the real window:** the same as T2 (the desktop is locked). The perf run did open the real release app and exercised `openFile` through Rust on the 1 MB fixtures, which is the one real-window evidence this task has.

## P2-T4

- **One field does three jobs.** `src/editor/lineEndings.ts` follows edits (breaks an edit adds take the ending of the line they came from, breaks after it keep theirs and shift), puts endings back on undo and redo, and carries endings with moved text. It lives on the master only; followers never see it, since the master gets the changes unchanged.
- **Undo restores endings through `invertedEffects`.** For every change in a transaction that removes breaks, history stores a `restoreBreaks` effect with the removed breaks' endings. The effect holds break indices in the document the undo lands in, not positions, so nothing has to map it. That is safe because nothing rebases history while it lives on one master. The external reload in T5 replaces the text and must clear the history, which it would have to do anyway. Redo works the same way, because history inverts the undo transaction too.
- **A move is recognised by its shape.** Exactly one deletion and one insertion of the same text moves the endings of the breaks inside the text with it. The plan floated an effect carried from the follower; the shape needs no carrying, covers the undo and redo of a move (same shape, so no stored endings), and matches what `moveSelectedText` makes (`userEvent: 'move.drop'`). A test in `tests/editor/lineEndings.test.ts` pins that shape for drops above and below the selection, so a change to `textDrag.ts` fails there first. The drag is still a spike that the app does not use (P5-T7), so moves are checked headlessly only.
- **The cost of the shape rule.** Two cursors where one deletes `\n\n` and the other types `\n\n` count as a move. Only the endings of the breaks typed there differ: they come from the deleted breaks, not from the line. No untouched line changes. The random test found this on its first run (run 5, a deletion and an insertion that happened to be the same two newlines); I kept the rule and made the generator skip such look-alikes, because the explicit tests pin the rule itself.
- **ISC-2 is split where the bytes are.** Rust owns every byte transform, so `edit_isolation_leaves_every_byte_outside_an_edit_unchanged` (in `src-tauri/src/fs/mod.rs`) takes 1000 random files in UTF-8, UTF-8 with a BOM and UTF-16 in both orders, with every ending and an emoji, a BOM character and a NUL in the mix. It applies one edit to the `\n`-only text with the endings following the page's rules (a plain list with one ending per break, sharing nothing with `eol.rs`), saves, and checks that the bytes before the edit, the bytes after it, and the new text between them are what they must be. 982 of the 1000 runs made an edit (the rest drew an empty one). Every generated file must open editable: one that opens read-only fails the test, so a broken round trip cannot hide as a skipped run. The page-side half, that the field gives Rust the right endings, is the TypeScript property test below.
- **ISC-3 on the fixture and at random.** On `mixed-eol.md` (367 lines, CRLF and LF), appending to, splitting, joining and deleting every line in turn leaves every other line's raw text identical, and undoing the deletion puts the whole file back. The random test (300 runs of 40 steps from random mixed files) mixes single edits, two-change transactions, drags, undo and redo, and compares the saved text after every step with a reference model that is an array of characters with an ending on each break. Undoing a whole run gives back the opened bytes, and redoing it gives back where it ended. After every step the stored endings must be in the shape Rust accepts: ascending, in range, never equal to the dominant one. `tests/helpers/endings.ts` has the test-side split and join (the page never splits raw text; Rust does).
- **Mutation proofs (the code broken on purpose, then restored):**
  - `join` ignores every exception, or puts one a break late: the Rust test fails on its first run because the file opens read-only (`run 0: ... opened read-only: Some(NotRoundTrippable)`). Before I made a read-only open a failure it still failed, on the count of runs that made an edit (208 of 1000).
  - Undo no longer restores endings: 6 TypeScript tests fail (the fixture undo, four undo tests, the random run).
  - A move is no longer recognised: 4 fail.
  - New breaks take the dominant ending instead of the line's: 4 fail.
  - Later breaks are not shifted after an edit: 14 fail.
  - The restored code passes all 37 tests in the file.
- **The spike's open item is closed.** The P0 spike test that recorded "does not restore a deleted ending on undo (known limit)" is gone; five undo tests and the move tests replace it, and the matching line is out of Remaining Work in `ISA.md`.
- **No UI claim here.** Nothing in this task has a screen to look at: the field is state, and the app does not wire the drag yet.

## P2-T5

- **Rust decides by content, not by event.** Each open document records the hash of what the page last read or wrote (`known_hash`). The watcher reads the file and compares; a match says nothing, whatever the event was. That makes events cheap to over-deliver: editors save with a temp file, a rename and a metadata change, a pull can touch a file twice, and a notify buffer can overflow. None of that needs special handling. A second field, `reported_hash`, stops one outside change being reported twice, and clears when the file goes back to what the document holds.
- **An own save is invisible because the hash goes in before the write.** `save_path_guarded` calls the caller with the hash it is about to write, and `save_document_with` records it as `known_hash` before the rename (the T2 version recorded it after, which left a window where the watcher thread could read the new file, find a hash nobody had recorded, and report mdmate's own save as an outside change). If the write fails the record goes back, unless something moved it on meanwhile. `Stage::AfterRename` lets a test act as the watcher thread at the exact moment, before the save returns.
- **A save refuses to overwrite a file that changed behind its back.** Just before the write, it reads the file and compares with `known_hash`; a difference is `AppError::DiskChanged` (kind `disk-changed`). A file that cannot be read (gone, or locked) does not refuse: the save recreates it, or fails with its own error. This covers whatever the watcher missed (a folder it could not watch, a dropped event, a change in the last 100 ms), so no path loses an outside change silently. The page turns the refusal into a conflict of kind `'save'`, and Keep mine then goes on to save.
- **Folders are watched, not files.** One `notify` 8 `RecommendedWatcher` watches the parent folder of each open document, non-recursively, with a per-document refcount so a folder is dropped when its last document closes. Event paths are matched to documents through a spelling key (the display path, lower-cased where the file system ignores case), the same comparison `Access` uses for its own keys. A dedicated thread coalesces: a path must be quiet for 100 ms before its file is read. A `need_rescan` flag or a watch error checks every open document. The thread holds the app state through a `Weak`, so it ends with the app.
- **A busy file is retried, a missing one is not news.** Reading a file while another program replaces it can fail on Windows with a sharing violation or access denied. `read_bytes_settled` retries up to five times, 40 ms apart, and only for errors the platform trait calls busy (`Platform::file_is_busy`, a new method: the check is OS-specific, so it sits behind the trait, which is what the `no-os-cfg-outside-platform` rule is for). A file that is gone after that says nothing and the tab keeps its text. It never reloads to empty.
- **Re-opening an open file no longer refreshes what Rust recorded.** `register` used to overwrite the entry (hash and format) when the same file was opened again. With a watcher that is a hole: the page still holds the old text, Rust would then think they match, and the save check would pass over a change the page never saw. Now an existing entry stays as it is, the frame carries the fresh content, and the page compares its hash with its own (`openPath` treats a mismatch as an outside change). A Rust test and a web test pin this.
- **The page handles a change in four steps, one at a time per document.** `noticeDiskChange` ignores a hash the document already has. A document with edits, or with a conflict already showing, raises a conflict and does not read the file at all, so the host's record stays old and its own check still guards a save. A clean document reads the file (`reload_document`), and applies it only if nothing was typed meanwhile (compared by text, so moving the caret does not count). Per-document serialising with an "again" flag means two reads can never be applied out of order. A read that brings nothing new (same hash) does nothing, so history is not wiped for no reason.
- **Reload starts the undo history over.** The history describes text that is gone, and T4 already noted this. `Document.reload` makes a new master (history, endings and read-only from the new content), keeps the caret by mapping it through the one smallest change between the old and the new text (common prefix and suffix, never cutting a surrogate pair), and sends that change to every follower, so a caret or scroll position away from the edit stays put. A file turning read-only (an encoding the app cannot write back) reaches every follower's editor: the read-only setting is now a `Compartment`, and `Follower.reconfigure` applies a change to it. That closes the "readOnly on reload does not update followers" gap I noted while designing this.
- **Keep mine measures the document against the disk's content.** `Document.adoptDisk` makes the disk's text the saved baseline without touching the document, so the tab stays marked as edited while its text differs, and is clean if the user's edits happen to equal the new file. The conflict banner (`PaneNotice.vue`, stacked under the close prompt when both apply) has two buttons; `resolveConflict(docId, 'mine' | 'theirs')` re-reads the file first, so it always compares with what is on disk at that moment.
- **A save is refused while a conflict is showing.** After a clean-looking read, the host believes the document is in step with the new file, so its own check would let a save through; the page therefore refuses to save while `conflict` is set and says why in `saveError`. The `Save` button of a pending close then reports the reason instead of silently doing nothing.
- **New code, commands and permissions.**
  - `notify` 8.2.1 (crate, see the table above): the OS file notifications. Pure Rust, no network.
  - `watch_changes(on_event: Channel<DiskChange>)`: starts the watcher, or only replaces the channel if it is running. The page calls it once after the window is shown, so it does not count against startup.
  - `reload_document(id)`: reads the file again and returns a frame like `open_file`; sets what the host has recorded for the document.
  - `perf_grant_file(path)` in `commands/perf.rs`, perf builds only: lets a harness open a file without the native dialog. It is what I used for the real-window check below, and `pnpm perf crash-restore` (T6) will use it too.
  - No new Tauri permission: all three are our own commands, and `tauri-plugin-fs` stays out. `check-arch` passes (`no-network` reads `notify` among the direct dependencies and finds nothing network).
- **Mutation proofs (the code broken on purpose, then restored):**

## P2-T6: Hot exit and session restore

- **What it does.** The page writes one snapshot of the session (the split layout, each tab's file and caret, and every unsaved buffer with the text, its line endings and the hash of the file it was typed on) to `session.json` in the data folder. It writes a short while after anything changes, and once more when the window is asked to close. The next start reads it before the first paint and puts everything back. Closing the app with unsaved edits asks nothing: the edits are in the snapshot (ISC-49).
- **New crates:** none. **New Tauri permissions:** none (the new commands are the app's own: `session_write`, `session_load`, `session_recover`, `watch_close`, `quit_app`; the perf build adds `perf_ready`).
- **Where the file lives.** The data folder is Tauri's app data folder, or the folder named by `MDMATE_DATA_DIR` when that variable is set. The variable exists so the perf harness and the tests never touch the real session; the harness gives every launch an empty folder of its own unless it asks to share one.
- **Rust owns the file, the page owns the content.** Rust writes with the same temp-file-and-rename as a save, so a crash leaves the last snapshot or the one before it, never half of one. It sweeps its own leftover temp files at start and moves an unreadable `session.json` aside instead of deleting it. The page sends the snapshot as raw UTF-8 in the request body, so a 4 MB buffer is not escaped a second time on the way through the invoke layer.
- **The page cannot grant itself files.** Rust adds the paths of the documents it has open to the envelope. At the next start `session_load` grants exactly those paths, and the page can only open what the last run itself opened. The paths the page writes into `tabs` and `buffers` are only names: opening one the grants do not cover fails like any other open of an ungranted path. This keeps "the page has no command that grants access" true. Someone who can edit files in the data folder can edit the grants too, but they could equally just run the app; that is outside what this protects.
- **Journal interval: 1000 ms.** The question was how often to write. Measured in the real release app on this machine (`pnpm perf journal-cost`, 11 repeats per size, each after an edit so the snapshot always changed):

  | Unsaved text | Snapshot | Build (page) | Until the host confirms | Longest gap between frames |
  |---|---|---|---|---|
  | none | 25 KB | 0.2 ms | 5 ms | 18 ms median, 39 ms worst |
  | 1 MB | 1.1 MB | 5 ms | 26 ms | 20 ms median, 27 ms worst |
  | 4 MB | 4.3 MB | 13 ms | 81 ms | 29 ms median, 34 ms worst |

  So a write costs the page about one late frame at 1 MB and two at 4 MB, once per interval and only while something changed. At 1000 ms that is at most 1 frame in 60 while typing in a 1 MB file, and a force-kill loses at most the last second of typing. A longer interval halves the late frames and doubles what a crash can lose; a shorter one does the opposite. 1000 ms stays. The write is throttled from the first change (not debounced), so continuous typing still reaches the disk every second.
- **Only one write at a time.** Two writes in flight could finish out of order and leave the older snapshot on disk. The journal runs one at a time: a request that arrives during a write sets a flag, and the write loop goes round once more with the newest state. Skipping a snapshot identical to the last one written keeps an idle app from writing anything.
- **Closing.** Rust's `CloseRequested` handler stops the close, asks the page over a channel, and starts a 3 s timer. The page waits for any write in flight, writes the newest state, and calls `quit_app`. If the page does not answer in 3 s, Rust closes anyway. A failed write does not stop the close; the app prefers losing a second of typing to refusing to quit.
- **Restore, step by step.**
  1. Open every file the session names, in parallel.
  2. Put each unsaved buffer back into its document before any tab is built, so a tab never shows the disk's version for a frame. A buffer is restored with its text and its line endings, and the document then counts as edited from the file's current content: clean if the two are equal, edited if not.
  3. If the file changed since the buffer was typed (the hash recorded in the snapshot differs from the file's), the tab shows the conflict banner from P2-T5 and the user picks Keep mine or Load theirs. Nothing is chosen for them.
  4. Rebuild the layout and the tabs. A tab whose file cannot be opened is dropped from the layout; carets are seeded for tabs that have no editor yet and clamped to the text, so a file that got shorter does not break one.
  5. The tab counter resumes after the highest restored id, so a new tab never reuses an id.
- **Nothing is dropped silently.** Text that cannot go back into a tab (its file is gone, its endings fail validation, its document is read-only or already restored, or the whole snapshot cannot be read) is written to a file in `recovered/` in the data folder, and a notice says where. The snapshot is then rewritten without it, so the next start does not recover it a second time.
- **The snapshot is untrusted input.** The page validates every field it reads. Endings must be ascending, in range for the text's line count, and none equal to the dominant ending (the same rules as Rust's frame decoder); a caret that is not a finite number becomes 0; a layout that does not parse leaves the tabs in one pane with a notice.
- **Proof it works, and that the proof can fail.**
  - `pnpm test:web tests/documents/session.test.ts` (26 tests) closes ISC-48: the layout is equal after a round trip, with splits, sizes, tab order and the active tab and pane. It also covers carets, edits with mixed endings saved byte for byte, buffers for a changed or missing file, damaged endings and layouts, the journal's timing, and the close flow.
  - Breaking the code fails the tests that guard it. One write at a time removed: 2 fail. Skip-identical removed: 1. Closing without flushing: 3. Interval set to 0: 2. Endings not validated: 1. One timer per burst of changes removed: 1 (only the retry-after-error test notices; the skip-identical rule hides the extra timers everywhere else). With the timer replaced by an immediate write, the suite hangs, because a failing write then retries in a tight loop; the real code retries only on the timer.
  - `pnpm perf crash-restore` closes ISC-47 in the real release app: phase 1 opens four files in two panes, makes unsaved edits in three (one with mixed line endings, one of 1 MB), waits for the journal to write by itself (911 to 931 ms after the last edit), and is killed with `TerminateProcess`. Phase 2 starts the app the normal way and reports what came back. The harness compares the layout, and for every tab the path, the edited mark, the caret and the SHA-256 of the bytes a save would write. Result: everything matches. With one letter of the saved session changed between the phases (`--corrupt`), the SHA-256 of the mixed-endings tab differs and the check fails as it should, so it can fail.
  - Real window with real typing (`cargo run --features perf`, WebView2 DevTools port, key input through CDP, 11 checks): typed into a file with mixed endings, waited 1.6 s, killed the process; the next start showed the tab with its edited mark and the typed text; Ctrl+S then wrote the file with `\r\n`, `\n`, `\r` kept where they were. Closing with an OS close request (`CloseMainWindow`) and again with the title bar's own Close button, 100 ms after typing and so well inside the interval, ended the app with no prompt; the next start had the text typed in those 100 ms. This is ISC-49.
- **Startup.** `pnpm perf startup` reports 597 ms with an empty data folder and 648 ms with a saved session holding 5 tabs and about 1 MB of unsaved text (restoring costs 84 ms of that, 94 to 115 ms by the scenario's own timer). The limit is 1000 ms. Both are under the 1000 ms limit, but the empty-folder number is above the earlier baselines of 419 to 480 ms. Part of the rise is in code this task did not touch ("Rust main to page start" went from 286 to 346 ms), and the CPU was only 70 to 80% idle before each launch against 87 to 96% before; the Vite dev server on port 1420 was using 1.3 cores during these runs. I did not stop it, because I could not tell whether it was started for this work, so the cause is not confirmed. Stopping it and running `pnpm perf startup` again settles it. Page start to app mounted also doubled (65 to 130 ms), which does fit a bigger bundle (the session code is in it) as much as a busy machine.
- **Known limits.**
  - Two instances of the app share one data folder, and the last one to write wins. Nothing stops a second instance yet; it needs a single-instance guard, which is a window-management decision for a later phase.
  - A force-kill loses what was typed after the last journal write (about a second) and nothing else.
  - **Not checked:** the native Open dialog; a crash while a write is in flight (the rename is the one saves use and is tested stage by stage there, but a real power cut was not); Windows shutdown or logoff closing the app (the close handler is the same one, but I did not log off).
