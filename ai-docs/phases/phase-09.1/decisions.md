## P9.1-T50: delete spike (ISC-781)

Progress and Cancel are too coarse during the move, so the plan's "stop and ask" applies. The owner read these notes (2026-11-27) and chose option 1 and guard B below. ISC-782, ISC-783 and ISC-788 are reworded to match.

**For a file or folder too big for the Recycle Bin, Windows shows a warning.** Yes destroys it. No keeps it whole and the operation reports that it was cancelled.

- **Setup.** A copy of this repository's `node_modules` in `D:\mdmate-spike\` (18,209 files, 2,318 folders, 281.6 MB). The copy leaves out pnpm's junctions (`robocopy /XJ`). A throwaway program outside the repository queued the one folder in an `IFileOperation` with the flags of `trash` 5.3.0 (`FOF_NO_UI | FOF_ALLOWUNDO | FOF_WANTNUKEWARNING`) and logged every progress sink call. Windows 11 Pro 10.0.26200, NVMe SSD, NTFS.
- **Time, three recycles of the whole folder:**

| Run | Shell counts | Shell moves | After the move | Total |
|---|---|---|---|---|
| 1 | 20.7 s | 78.1 s | 1.6 s | 100.6 s |
| 2 | 9.3 s | 4.3 s | 1.2 s | 14.9 s |
| 3 | 4.1 s | 3.2 s | 0.4 s | 7.7 s |

  Why the runs differ so much was not looked for. A plain `std::fs` walk that counts the same tree took 0.06 to 0.35 s.
- **Progress.** While counting, `UpdateProgress` comes about once per item (20,529 calls), with 0 done of 0, and the last of them gives the total. Then one `PreDeleteItem` for the top folder. During the move there is no call at all. Then one `PostDeleteItem` and one `UpdateProgress` with all done.
- **Recycle Bin.** One entry for the folder, 281,643,702 bytes. Restoring it took 6.0 s and gave back the same files, folders and bytes.
- **A normal recycle.** `PreDeleteItem` received the flags `0x282`, which include `TSF_DELETE_RECYCLE_IF_POSSIBLE` (`0x80`), and `PostDeleteItem` `0x270008` with a new item inside `$Recycle.Bin`.
- **Too big for the bin** (limit 3,749 MB, a dummy file of 4,773 MB). Windows showed warnings although `FOF_NO_UI` was set, and the owner answered Yes to each. Which cases showed one was not recorded. Every result below is after a Yes. The bin did not change.

|---|---|---|
| The file, refusing when `0x80` is missing | `0x282`, then `0x270008` with no new item | Destroyed |
| The file, `trash` flags | The same | Destroyed, `Ok` |
| A folder holding it, refusing | The folder: `0x282`, then `0x270003` (not handled) with no new item. The file: `0x2` | Refused, file kept, operation aborted |
| The same folder, `trash` flags | The same calls, then `0x270008` with no new item for the file | File and folder destroyed, `Ok` |

  So `0x80` was missing only for what is inside a folder too big to recycle. The item queued as a file carried it and was destroyed. `0x270003` also comes with no new item and by itself lost nothing.
- **Answering No** (a second test, the same flags):

| Case | Warning | Result |
|---|---|---|
| A file of 4,773 MB | Asked to delete it permanently | Kept |
| A folder holding it and a small file | Asked the same for the folder | Folder and both files kept |
| A folder of two 2,500 MB files | Asked the same for the folder | Folder and both files kept |
| A file of 3,685 MB, with 281 MB already in the bin | None (0.1 s) | In the bin. Both older entries were still listed, and the bin held more than its limit |

  After No, `PostDeleteItem` and `PerformOperations` returned `0x80270000` (`COPYENGINE_E_USER_CANCELLED`) and `GetAnyOperationsAborted` said true. The results are consistent with "too big" meaning over the bin's limit (3,749 MB) rather than over the room left in it, with a folder counted as a whole. The exact cutoff between 3,685 and 4,773 MB was not measured.

  - B (recommended). Refuse it. With the sizes from the counting walk, leave out what the bin cannot take before queuing, and report it as kept. ISC-784 stands. It rests on the bin's limit read from the registry (`MaxCapacity`), so the warning stays on behind it for what the check misjudges or cannot size, a `PreDeleteItem` without `0x80` is still refused, and anything destroyed is reported.
  - Not measured, and in favour of B: in A, a No may cancel the rest of a selection (ISC-786), and the warning comes in the move, where the app's Cancel cannot act, while the progress dialog is up (ISC-788).

## P9.1-T12: Ctrl+Tab cycles the tab-list menu

- **Palette run.** The Cycle Tabs commands run from the command palette have no key press, so there is no release to wait for. They switch to the next or previous tab at once, with no menu. The plan did not say.
- **Focus stays put.** The menu the cycle opens does not take focus: the keys that drive it (Tab, the arrows, Escape, Enter, the release of Ctrl) are read by the page, so the editor keeps its caret and CodeMirror never sees them. Committing puts the caret in the editor of the tab switched to.
- **Ways out.** Besides the release of Ctrl and Escape, the cycle ends with no switch when the window loses focus (a release that never arrives) and when another pane takes the focus. A click outside the menu cancels it too.
- **Open risk (ISC-604).** Whether WebView2 hands Ctrl+Tab to the page was not tried; `disable_browser_keys` is set but nothing has used this chord. The owner checks it in `pnpm tauri dev`.

## P9.1-T17: Remember the window size, position and maximised state

- **Rust remembers the normal bounds.** A maximised window reports the whole screen, so `WindowMemory` keeps the last bounds seen while the window was not maximised, minimised or full screen (`window_state::current`, called on every `Moved` and `Resized` and by `window_geometry`). A maximised window is saved as those bounds plus `maximized: true`. The page does not track the normal size itself.
- **Inner size, outer position.** `set_size` takes the content size and `set_position` the outer position, so the saved value is the pair Tauri takes back. The window has no frame, so the two sizes are the same.
- **Where it is in the file.** `window` sits at the top of the snapshot, beside `workspace`, and is left out until the host has answered once. Old files have none and the version stays 1.
- **Reachable, not inside.** The guard keeps a window that is partly off a monitor while at least 100x50 px of it lie on one (enough to grab the title bar). Entirely off every monitor, or larger than the monitor it mostly lies on, it is centred on the first monitor (the primary), at the saved size reduced to fit. The work area is used, so it does not go under the taskbar. A monitor smaller than the minimum cannot hold the window; it starts at that monitor's corner.
- **Placement order.** Position, size, position: moving a window to a monitor with another scale can resize it, and the last move puts it back.
- **Maximise before show.** `restore` maximises while the window is still hidden. Whether WebView2 keeps it hidden through that was not looked at; the owner watches the start for a blank frame.
- **Known limit.** Dragging a window to the top edge to maximise it moves the window first, so the normal bounds saved are where the drag ended, not where it began. Windows keeps its own record of that, which would need Win32 `GetWindowPlacement`; not done.
- **Open (not part of ISC-617/618).** The look in the real window: size, place, maximised, a second monitor, unplugged monitor. The owner checks it in `pnpm tauri dev`.

## P9.1-T19: List markers are drawn as an en dash

- **Width.** The widget is a hidden hyphen that sets the width, with the en dash laid over it (`bullet.ts`). In a monospace font the two glyphs are equally wide. In a proportional body font the dash is wider than a hyphen and overhangs into the space after the marker; the text does not move, so continuation lines of a wrapped item still line up. This was not looked at on screen.
- **A new item type.** The scan returns `bullet` (like `checkbox`) instead of the `mark` for `-`, `*` and `+` when the selection is away. The raw marker with `cm-md-list-mark` is the same as before while it is touched, and ordered markers (`1.`, `2)`) never change.
- **Caret.** The bullet is added to the set the caret steps over (`hiddenFor`), like hidden syntax. Because a selection that touches the marker (edges included) shows the raw marker instead, the caret never sits inside a drawn dash; a walk with the arrow keys visits every position.
- **Click.** The widget ignores no events (`ignoreEvent` false), so a click on the dash puts the caret by the marker, which then shows raw.
- **Copy.** Copying reads the document, so it gives the Markdown text. CodeMirror answers a copy only for a focused editor, so the copy tests focus the view.
- **Open.** There is no manual claim for T19. The plan's "the owner finds the dash right in Dark, Light and Sepia" is the owner's look at the real window.

## P9.1-T25: Searchable font comboboxes

- **`fontdb` 0.24.0, pinned with `=`.** Approved by the owner. Licences (from `cargo metadata`): fontdb MIT, fontconfig-parser MIT, libc, log, memmap2 and roxmltree MIT or Apache-2.0, slotmap Zlib, tinyvec Zlib or Apache-2.0 or MIT. All are permissive and fit the project's MIT. Default features are kept (the fontconfig reader matters on Linux only). Five crates are new in `Cargo.lock`.

## P9.1-T52: permanent delete

- **Its own walk.** `platform/purge.rs` removes item by item and has no OS code. A link is removed as a link. Before a folder's contents go, `hold_folder` holds it; Windows opens it without sharing delete or write and refuses a link, so a folder swapped for a junction before the hold is not entered, and a held one cannot be renamed or removed. Not verified: whether another program can turn a held folder into a junction in place; NTFS allows that only on an empty one.
- **Its own command.** `delete_permanently` takes the paths and nothing else; no argument of `delete_entries` can ask for it. Both share the one turn, so `delete_cancel` and the wait on close cover it.
- **Progress differs from a recycle** (plan: same engine and dialog). The count, the nesting of targets and the report are the engine's. The walk adds a `removing` phase with a percent, and Cancel acts until the end. A recycle's phases would have given no percent at all.
- **Its own end.** What it removes ends as `Removed` and is reported as deleted, so the toast about a file removed for good, which is for accidents, stays away.
- **Refusals.** All a delete to the bin refuses, and a folder that holds a workspace root: it would take the root with it. One refusal rejects the whole selection.
- **Partly removed folders.** A cancelled or failed delete can leave a folder without some of its files. The page then closes the tabs of the files that are gone, unsaved ones included, and keeps the rest.
- **Read-only and locked.** A read-only mark is lifted for the removal and put back if the item stays. A file in use stays, with its folders, and the toast names it.
