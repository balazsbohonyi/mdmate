# Phase 1 decisions

Deviations from the plan and choices it left open. Numbers carry the OS they came from.

## Checking the UI (all of Phase 1)

- **Browser checks use Claude in Chrome, not Interceptor.** The ISA rows say "Interceptor on pnpm dev". Interceptor 2.1.6 is installed here, but its isolation gate exits 5 ("no browser contexts connected"): the test profile and its extension were never set up on this machine, and doing that is a one-time step in the owner's own Chrome. Claude in Chrome drives the same real Chrome and works today, so each Verification stub names the tool that ran. The ISA rows keep their wording; this note is the substitution.
- **`pnpm tauri dev` screenshots come from WebView2 itself.** The app starts with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222`, and a small Chrome DevTools Protocol script (kept outside the repo) saves `Page.captureScreenshot` and runs page scripts. That is the real WebView2 rendering the real app. It does not show the window frame or anything the OS draws.

## P1-T1

- **Palettes: "Graphite" (dark) and "Paper" (light), written from scratch.** Dark is cool slate surfaces at hue 262 around `#1d2027`, with one mint accent at hue 182. Light is warm paper at hue 85 with the same accent family darkened. Syntax colors sit around the wheel at similar lightness within each theme. I chose them to be calm for long reading, with the accent kept to focus, caret and links. No value comes from a SublimeText or other editor theme (ISC-146 is checked by the owner later).
- **A test, not a taste call, holds the palettes honest.** `tests/styles/themes.test.ts` checks that dark and light define the same tokens, that every token maps to a Tailwind utility, that no color lives in `tokens.css`, that every color is inside the sRGB gamut, and that 29 text-on-surface pairs meet their contrast ratio (7 for body text and the active tab, 4.5 for other text, 3 for the dimmed syntax marks and comments). It caught two real mistakes in my first light palette: an accent outside sRGB, and a syntax mark at 2.98.
- **Colors live in `src/styles/themes/dark.css` and `light.css`, and nowhere else.** `tokens.css` holds fonts, the type scale, chrome sizes, radius and the `@theme inline` map. The theme class goes on `<html>`: `dark` or `light`. With no class the page is dark, because `:root` carries the dark values, and `index.html` sets `dark` anyway so the first paint is right.
- **The window background changed from `#1e1f22` to `#1d2027`.** It is the dark `--background`, repeated in `tauri.conf.json` because the native window paints before CSS loads. A test pins the pair, so they cannot drift. The native window stays dark even when the light theme is chosen; it shows only after first paint, so a light-theme user sees no dark flash.
- **Dropped the chart tokens and `sidebar-primary` and `sidebar-ring`.** shadcn-vue's `init` generated them, nothing here uses them, and `add` does not need them. Radius went from 0.625rem to 0.25rem for a squarer, denser frame.
- **Added workbench and editor tokens now.** Titlebar, tab strip, active tab, status bar, split handle, drop preview, selection, caret and 16 syntax tokens, so Phase 1 chrome and Phase 3 styling start from names that already exist in both themes.
- **Sizes are Tailwind theme values** (`--spacing-titlebar` and friends give `h-titlebar`, `w-sidebar`). Tailwind leaves a theme value out of the CSS until something uses it, so they show up in the built CSS from T2 on.
- **`no-hard-coded-colors` now also catches Tailwind palette classes** (`bg-white`, `text-slate-500`, `border-t-red-500`, with opacity or in a template string). They are hard-coded colors that no theme file can change, so ISC-14 is false while they exist. Five planted cases and a clean case with look-alike words are in `tests/scripts/checkArch.test.ts`. **Not checked:** named CSS colors such as `red`, which turn up in prose and identifiers far more than in color positions.
- **ISC-14's probe already passed before any work** (zero matches, because almost no UI existed). By the ISA standard that means the claim is redundant or the probe cannot fail, so the proof that it can fail is the planted tests, and the new palette-class cases widen what it can see.

## P1-T2

- **The window capability grows by four permissions.** `core:window:default` lets a page toggle maximize and read its state, but not start a drag, minimize, toggle maximize through the normal command, or close. A probe (`invoke('plugin:window|<cmd>', { label: 'nope' })` answers "not allowed" or "window not found") showed all four denied, so `capabilities/default.json` now adds `allow-start-dragging`, `allow-minimize`, `allow-toggle-maximize` and `allow-close`. The same probe now answers "window not found" for each.
- **Dragging uses `data-tauri-drag-region` on the title area.** The "mdmate" label inside it is `pointer-events-none`, because Tauri only drags when the press lands on the marked element itself. A real mouse drag on it moved the window by exactly the dragged distance, in both directions, and a double-click toggled maximize. Phase 0 had only tested a Rust `start_dragging` command.
- **Caption buttons are Vue buttons behind `host.windowControls`** (minimize, toggle maximize, close, is maximized, a maximized-change listener), so `@tauri-apps` stays in `src/platform/`. The maximize icon becomes Restore from the window's resize events. No snap-layout hover flyout, as decided in Phase 0.
- **The shadcn-vue wrapper was built here, when the first component was added, not at Resizable.** `pnpm ui:add <name>` runs `shadcn-vue@2.9.0 add` (never `init`), puts back `tokens.css`, `components.json` and `src/lib/utils.ts` if the add touched them, and puts the `ts-nocheck` line back in every generated file. It is idempotent: a second run left every hash unchanged, and deleting the line from two files was repaired byte for byte by `pnpm ui:add --mark-only`. A new `ui-files-marked` rule in `check-arch` fails on a generated file without the exact line (8 tests, 7 of them planted). I read the script and the config diffs myself and re-ran every gate. The add also installed `reka-ui` 2.11.0 and `@vueuse/core` 15.0.0, which the generated files import.
- **Six ESLint rules are relaxed for `src/components/ui/**/*.vue`, not five.** The marker line itself trips `@typescript-eslint/ban-ts-comment` in every generated file, which the Phase 0 notes missed. It is set to allow `ts-nocheck` with a description (the marker's `-- reason` counts), so any other suppression comment stays banned there. The five named rules are off, and the folder is in `.prettierignore`.
- **The shell shows a placeholder "Welcome" tab until T4,** so the tab strip is visible and sized. The menu has two static entries (Toggle Sidebar, Exit) until the command registry in T6, and the sidebar-visibility store came early because the menu needs it.
- **Startup is 435 ms median with the shell** (5 runs, spread 4%, 2 warm-ups), against 1000 ms. The bare shell took 429 to 475 ms. Most of it is Rust main to page start (277 ms), which is WebView2 starting.
- **The launch recording needed a better instrument than I first used.** `gdigrab` delivered 33 frames a second with gaps up to 50 ms, and my first scan padded the video to 60 fps by copying frames, which put the frame numbers out of step with the decoder. The final check uses `ddagrab` (DXGI desktop duplication, 58 to 59 delivered frames a second, worst gap 34 ms), reads each real frame once with its own timestamp, and scans the window rectangle for near-white pixels. It is dark in every frame of 8 launches, and the window first appears as the dark UI mid-way through Windows 11's open fade. **What it cannot see:** a white flash shorter than about two frames. A control window white for about 100 ms was caught; one up for 43 ms was not. The tools are in my scratchpad, not the repo.
- **Minimize and close were tested on the release build, maximize and restore in `pnpm tauri dev`.** Close needed a window I could afford to lose, and the release build has the same shell code. The window is found by title through the process's top-level windows, since `MainWindowHandle` points at a 16 by 16 helper window once the real one is minimized.

## P1-T3

- **The model is pure functions over an immutable `Layout`** (`root`, `activePane`, `nextId`), in `src/workbench/splitTree.ts`, with no Vue and no document logic. A tab is only an id until Phase 2. Every function returns a new layout, or the same object when nothing changes, so a store, a test and a saved session share one set of rules.
- **Split nodes carry an id, which the TypeScript standard's example does not.** Rendering keys groups by it, and a resize has to name the split it changes. Ids come from a counter in the layout (`p3`, `s4`), so they are deterministic and survive a save.
- **Sizes are percentages summing to 100, with one rule for who gets freed space.** A closed pane's share goes to the previous sibling, or the next one if it was first. Splitting a pane halves its own share, so siblings keep theirs. `setSizes` scales whatever it is given to 100 and ignores a wrong count, a size of zero or less, or a non-finite size.
- **A split never has the direction of its parent.** Closing a pane or moving a tab can leave a column inside a column, so every removal re-flattens the tree, multiplying the inner sizes into the outer ones. The tests plant that case and a collapsed split with one child.
- **Closing the last tab of the only pane leaves it empty** (ISA Decisions row). With one pane there is nothing to give its space to.
- **`moveTab` takes the index in the strip after the move.** It clamps a position past either end, and works within a pane (reorder, ISC-176) and across panes (ISC-32). `moveTabToEdge` splits a pane at one of four edges (ISC-33), and does nothing for the only tab of a pane on its own edge, which would leave an empty pane beside it.
- **Saved layouts are validated, not trusted.** `deserialize` takes text and reads it as `unknown`, with type guards and no casts, then runs `validateLayout`, which names every broken invariant (duplicate ids, a tab in two panes, sizes that do not add up, an active tab that is not in its pane, a split of one child). A bad file returns an error and never a half-built tree.
- **Proof the tests can fail:** the probe file did not exist at the start of the task, so every claim began failing. After that I broke the model three ways (no same-direction merge, closing a last tab keeps an empty pane, no collapse of a one-child split) and they made 2, 5 and 9 tests fail; the restored file passes all 55. A seeded property test (300 sequences of 60 random operations, replayable from the seed) checks validity, tab conservation and the serialize round trip after every step.

## P1-T4

- **A small store holds the live layout.** `src/workbench/store.ts` keeps the `Layout` in a shallow ref, replaced whole on every change by the pure functions from T3, plus a title for each tab id (a stand-in until Phase 2 has documents). It is a module-level store, as the architecture says, with no Pinia. Titles of closed tabs are dropped on every change.
- **The tree renders recursively** (`SplitNodeView`): a pane becomes `PaneView` (its tab strip and a body), a split becomes a shadcn-vue `ResizablePanelGroup` with a panel per child and a handle between them. Tab strips stay custom, as the plan says.
- **Panel sizes flow one way, so nothing jumps.** The model gives each panel a `default-size` once, when its group is built, and the group owns the sizes while you drag. They are written back to the model when the drag ends (the handle's `dragging` event), or at once for a keyboard resize, and a `layout` event that repeats the saved sizes writes nothing. A group is keyed by its split id and its children's ids, so it is rebuilt only when its children change, and then from the saved sizes. Feeding every emit back into `default-size` would rebuild panels mid-drag, so it is not done.
- **Checked in a real browser on `pnpm dev`:** three handles dragged with trusted mouse input, each pane and group node kept its identity through the drags, the model matched the DOM to the pixel, and a split of the active pane left every other pane's size alone. Arrow keys on a focused handle moved it by 10 points a press and saved. Not checked in `pnpm tauri dev`: the plan asks for that at T5, and T4 changes nothing that depends on the WebView.
- **Panes may not shrink below 6%,** so a handle can never swallow a pane, and the pane with focus shows its active tab with the accent line, while other panes' active tabs get a muted line. Clicking anywhere in a pane focuses it (capture phase, so a click on a button inside does too).
- **The dev seed is a three-level layout** (`row(pane column(pane row(pane pane)))`, nine tabs) called from `AppShell` behind `import.meta.env.DEV`. Release builds drop the branch and start with one empty pane saying "Open a file to start writing."
- **Nine store tests** cover opening, title pruning, splitting with and without a title, moving a tab to a pane and to an edge, selecting, resizing and the seed's shape. Removing the pruning makes one of them fail.
