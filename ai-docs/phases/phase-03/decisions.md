## P3-T1: Inline layer and headings

- **One pure function says what the layer does.** `scanPreview(state, ranges)` (`src/editor/livePreview/scan.ts`) reads the syntax tree over the ranges and returns plain items: `hide`, `mark` and `line`. The `ViewPlugin` scans `view.visibleRanges` and turns the items into decorations. The atomic ranges and the transaction filter of P3-T4 will scan around the caret with the same function, so what is drawn, what is atomic and what a selection may not enter cannot drift apart, and a test reads the answer from a plain `EditorState` with no view. Parked followers have no view, so anything that must hold for them has to work from state too.
- **Reveal rule.** An inline element shows its syntax when any selection range touches it, edges included (`from <= element.to && to >= element.from`). A block marker shows when a range touches its line. The test fixes both edges (position 0 and the end of the line reveal, the first position of the next line does not).
- **Headings.** ATX headings get a line style per level, and hide the hashes plus the blanks after them. A closing run (`## Title ##`) hides with the blank before it. A bare `#` stays, because hiding it would leave an empty line. **Setext headings** (`Title` over `=====`) get the line style, and the underline stays visible and muted: hiding it would leave an empty line with nothing to land the arrow keys on. This is my choice, not in the plan.
- **Wired inside the parser branch.** `createFollowerState` adds the layer next to the Markdown parser, so a tab that opens as plain source gets neither. Without a parser there is no tree, so the layer would do nothing there anyway: putting it on the plain path on purpose did not fail the view test, which is why that test instead breaks the size decision itself (`Document` ignoring `isLargeFile`), and that one fails. `createState` (standalone editors, the perf scenarios) takes `preview: true`, off by default.
- **The perf scenarios run the real layer.** `throwawayDecorations.ts` is deleted. The `decorations` knob became `preview` (default 1; `--set preview=0` is the plain-CodeMirror baseline, written to files with `-nopreview`). Scenarios that open through `Document` (open, tab switch) now always have the layer, as the app does. Runs with preview on add `probePreview()` counts to their values.
- **ISC-63 and how it was first done wrong.** The first scenario timed single scans with a clock that ticks in tenths of a millisecond, so every median came out 0 and the run "passed" with a null ratio. The second compared two different fixtures, which showed different content (12 items against 4) and failed on the work, not the size. The final one builds the 10 MB document as the 1 MB fixture ten times, so both views show the same text, one deep inside a tree ten times as big, times batches of 500 scans, requires the same item count, fails on a zero median, and includes a control that scans the whole document, which must be at least 3 times slower at 10 MB or the check could not tell flat from not flat. The harness exits non-zero when the scenario sets `checkFailed`.
  - Result (release app, Windows 11, Ryzen 7 8840HS, WebView2 157, 3 rounds): middle 14.2 µs at 1 MB against 13.8 µs at 10 MB (0.97), late 17.6 against 19.6 µs (1.11), limit 20%. Control: 2.6 ms and 24 ms (9.2 times).
  - **Not checked:** the layer is headings only, so a scan does little work (4 to 12 items). The claim is rerun with the full layer in P3-T6. The 10 MB document here is repeated text, not the generated `realistic-10mb.md` (whose viewport shows different content); the real 10 MB fixture is not measured for this claim. The tree was forced to parse to the end of the viewport first; how long the app takes to parse that far after opening a 10 MB file is a separate cost (it is above the 3 MiB cutoff in the app anyway).
- **Mutation proofs (the code broken on purpose, then restored):**
  - Edge-inclusive touch made exclusive: 1 test fails (the caret-on-the-edge test).
  - A bare `#` hidden: 1 fails.
  - The blank after the hashes left visible: 13 fail.
  - `Document` ignoring the size cutoff: the large-file view test fails.
  - Layer added to the plain-source path: nothing fails (see above), recorded rather than hidden.
  - The restored code passes all 20 heading tests and the 6 view tests.
- **Checked in Claude in Chrome (`pnpm dev`):** README.md opens with its heading hash shown while the caret is on it, and the hash is gone after clicking into the paragraph below.
- **Checked in the real window** (debug build against the Vite server, DevTools port): a file with three headings, a `#hashtag` line and a `## Second ##` heading. With the caret away every heading line shows its text only (`First heading`, `Second heading`, `Third`) with the heading line classes, the `#hashtag` line is untouched; with the caret on line 1 it shows `# First heading`. Screenshot taken.
- **Not checked:** headings inside lists and block quotes (lists and quotes arrive in T3), a heading while an IME composition is active, and how it looks in the light theme. The text is monospace; the preview does not change the editor font, which is outside every Phase 3 claim.
- **The Vite server I started is still running.** I stopped the background task, but its `node` process survived and an attempt to stop it by process id was refused, so I left it. The next tasks need it for the browser checks anyway; it must be stopped before the startup measurement in P3-T6.

## P3-T2: Emphasis and inline code

- **The parser is now GFM, in one place.** `src/editor/markdownSupport.ts` is `markdown({ base: markdownLanguage })`, used by the app and by the test helper. The default `markdown()` is CommonMark, which has no `Strikethrough` node (the advisor flagged it, and `tests/editor/markdownSupport.test.ts` shows `~~x~~` parses with GFM and not without), and Phase 4 needs GFM tables and task lists anyway. **Effect on speed, not measured here:** the P0 typing numbers were taken with the CommonMark parser, and GFM adds block and inline parsers. P3-T6 measures typing, open and tab switch with the final parser and layer, so nothing is claimed about it until then.
- **What each element does.** Bold, italic, strikethrough and inline code get a style over the whole element (markers included, which are then hidden), and each marker child is hidden unless the selection touches the element, edges included. Nested elements reveal on their own: the caret in `*italic*` inside `**bold ...**` shows both pairs, and the caret in the bold text outside the italic shows only the bold pair. Inline code gets the mono font, the code color and the code background from tokens; no new tokens.
- **Left as the parser decides:** intraword underscores (`snake_case_word` is not italic), unclosed markers, escaped markers, a single tilde. These are tested as "stays untouched" so a parser change that starts matching them fails.
- **Mutation proofs (the code broken on purpose, then restored):** wrong strikethrough mark name: 2 tests fail. Caret ignored (always hide): 10. Italic node left out: 4. Inline code mark left out: 4. The restored code passes all 104 editor tests.
- **Checked in Claude in Chrome (`pnpm dev`):** italic, bold, strikethrough and code render in one line; the caret in `**bold**` showed that pair only, on a word showed none, in `` `code` `` showed its backticks; the document text was identical after every move. The heading underline from CodeMirror's default highlight style is gone.
- **Checked in the real window:** `inline.md` with the caret on the last line shows `Some italic, bold, strike and code in one line.` and `Nested bold with italic inside here.` with the right styles (screenshot); the caret in the first of two bold spans reveals that span only; in `` `code` `` its backticks; in the nested italic both pairs.
- **A trap in my own driver.** The first real-window runs opened the file through `import('/src/documents/store.ts')`, but the Vite server had seen edits since the app loaded, so the app imported the store with a `?t=` stamp and my import made a second copy with its own document map. The tab existed, its document did not, and the pane stayed blank. Not a product bug (the same trap as in P2-T5). The driver now takes the module URL from the app's own resource entries.
- **Not checked:** emphasis inside link text (T3), inside block quotes and list items (T3), intraword emphasis next to CJK text, and the light theme. Typing speed with GFM and the layer is P3-T6.

## P3-T3: Links, lists, blockquotes and rules

- **Links.** `Link` nodes (inline, reference and shortcut) get the link style over the whole node. Away from the caret the opening `[` and everything from the closing `]` to the end of the node are hidden, so `[text](url "title")`, `[text][ref]` and `[text]` all read as `text`. The caret anywhere in the node, edges included, shows all of it. Hidden ranges are cut at line breaks (`hideLines`), so a title that wraps never produces a hidden range across lines. A link with no text (`[](url)`) is left raw: hiding it leaves nothing to see or to put the caret on, the same call as the bare `#`.
- **Autolinks and bare URLs.** `<http://x>` hides its angle brackets and styles the address; a bare `http://x` is only styled. A `URL` node inside a link, image, autolink or reference definition is not styled on its own (`addressed` set), so nothing is marked twice.
- **Left alone on purpose:** images (`![alt](src)`, no claim in this phase covers them) and reference definitions (`[ref]: url`), which are the one place the address is the content.
- **Lists.** Markers (`-`, `*`, `+`, `1.`, `2)`) get a marker style and are never hidden, so nothing can stick on them. I did not add a hanging indent or a `cm-md-li` line class: nothing in ISC-54 needs it, and padding on list lines is the kind of change that has to be re-checked against the arrow-key walk in T4.
- **Blockquotes.** Every line of a quote gets one line style (a nested quote and a lazy continuation line included, tracked by line start so a line is never styled twice). Each `>` and the blank after it hides unless the caret is on that line; a marker with nothing after it stays, so an empty quoted line keeps a character to land on. The style is a left bar plus padding on the line (not a margin, per the CodeMirror gotcha). Nested quotes look the same as outer ones.
- **Rules.** `HorizontalRule` gets a line style with a bottom border and its text hides unless the caret is on that line. The border sits at the bottom of the line, so with the text shown it is a rule under `---` rather than through it.
- **Mutation proofs (the code broken on purpose, then restored):** link ignores the caret: 3 tests fail. One hidden range across lines: 1. Empty link hidden: 1. URL rule widened to links: 2. Autolink brackets kept: 1. List marker style removed: 2. Quote lines styled twice: 1. Empty quote marker hidden: 1. Quote marker ignores the caret: 2. Blank after the marker left visible: 4. Rule never hides: 2. Rule ignores the caret: 2. All 12 are caught; the restored code passes all 540 tests.
- **Checked in the real window** (`blocks.md`): with the caret on the last line the link reads `docs`, the autolink reads `http://auto.example.com`, list markers are dim and the text is unchanged, the quote has its bar and no `>`, the rule is a line across the pane. With the caret in the link the full `[docs](http://example.com/docs "Docs")` shows; in the nested quote only that line shows `> > nested quote`; on the rule line `---` shows. The document length was the same after every move. Screenshots taken.
- **Not checked:** the light theme, an image next to a link, a heading or a code block inside a quote or list, a link split by an IME composition, and mouse clicks on hidden syntax (T4).
