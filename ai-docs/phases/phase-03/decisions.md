# Phase 3 decisions

Deviations from the plan and choices it left open. Numbers carry the OS they came from.

## Checking the UI (all of Phase 3)

- **Two places, every UI claim.** Claude in Chrome on `pnpm dev` (mock host), and the real app: `cargo run --features perf` from `src-tauri` against the same Vite server, `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222`, `MDMATE_DATA_DIR` pointing at a temp folder so the real session is never touched, trusted key and mouse events and screenshots over the DevTools port. Files are opened through `perf_grant_file` and the page's own store.

## P3-T1: Inline layer and headings

- **One pure function says what the layer does.** `scanPreview(state, ranges)` (`src/editor/livePreview/scan.ts`) reads the syntax tree over the ranges and returns plain items: `hide`, `mark` and `line`. The `ViewPlugin` scans `view.visibleRanges` and turns the items into decorations. The atomic ranges and the transaction filter of P3-T4 will scan around the caret with the same function, so what is drawn, what is atomic and what a selection may not enter cannot drift apart, and a test reads the answer from a plain `EditorState` with no view. Parked followers have no view, so anything that must hold for them has to work from state too.
- **Reveal rule.** An inline element shows its syntax when any selection range touches it, edges included (`from <= element.to && to >= element.from`). A block marker shows when a range touches its line. The test fixes both edges (position 0 and the end of the line reveal, the first position of the next line does not).
- **Headings.** ATX headings get a line style per level, and hide the hashes plus the blanks after them. A closing run (`## Title ##`) hides with the blank before it. A bare `#` stays, because hiding it would leave an empty line. **Setext headings** (`Title` over `=====`) get the line style, and the underline stays visible and muted: hiding it would leave an empty line with nothing to land the arrow keys on. This is my choice, not in the plan.
- **Wired inside the parser branch.** `createFollowerState` adds the layer next to the Markdown parser, so a tab that opens as plain source gets neither. Without a parser there is no tree, so the layer would do nothing there anyway: putting it on the plain path on purpose did not fail the view test, which is why that test instead breaks the size decision itself (`Document` ignoring `isLargeFile`), and that one fails. `createState` (standalone editors, the perf scenarios) takes `preview: true`, off by default.
- **The perf scenarios run the real layer.** `throwawayDecorations.ts` is deleted. The `decorations` knob became `preview` (default 1; `--set preview=0` is the plain-CodeMirror baseline, written to files with `-nopreview`). Scenarios that open through `Document` (open, tab switch) now always have the layer, as the app does. Runs with preview on add `probePreview()` counts to their values.
- **ISC-63 and how it was first done wrong.** The first scenario timed single scans with a clock that ticks in tenths of a millisecond, so every median came out 0 and the run "passed" with a null ratio. The second compared two different fixtures, which showed different content (12 items against 4) and failed on the work, not the size. The final one builds the 10 MB document as the 1 MB fixture ten times, so both views show the same text, one deep inside a tree ten times as big, times batches of 500 scans, requires the same item count, fails on a zero median, and includes a control that scans the whole document, which must be at least 3 times slower at 10 MB or the check could not tell flat from not flat. The harness exits non-zero when the scenario sets `checkFailed`.
  - Result (release app, Windows 11, Ryzen 7 8840HS, WebView2 157, 3 rounds): middle 14.2 µs at 1 MB against 13.8 µs at 10 MB (0.97), late 17.6 against 19.6 µs (1.11), limit 20%. Control: 2.6 ms and 24 ms (9.2 times).
  - **Not checked:** the layer is headings only, so a scan does little work (4 to 12 items). The claim is rerun with the full layer in P3-T6. The 10 MB document here is repeated text, not the generated `realistic-10mb.md` (whose viewport shows different content); the real 10 MB fixture is not measured for this claim. The tree was forced to parse to the end of the viewport first; how long the app takes to parse that far after opening a 10 MB file is a separate cost (it is above the 3 MiB cutoff in the app anyway).
- **Mutation proofs (the code broken on purpose, then restored):**
  - Edge-inclusive touch made exclusive: 1 test fails (the caret-on-the-edge test).
  - A bare `#` hidden: 1 fails.
  - The blank after the hashes left visible: 13 fail.
  - `Document` ignoring the size cutoff: the large-file view test fails.
  - Layer added to the plain-source path: nothing fails (see above), recorded rather than hidden.
  - The restored code passes all 20 heading tests and the 6 view tests.
- **Checked in Claude in Chrome (`pnpm dev`):** README.md opens with its heading hash shown while the caret is on it, and the hash is gone after clicking into the paragraph below.
- **Checked in the real window** (debug build against the Vite server, DevTools port): a file with three headings, a `#hashtag` line and a `## Second ##` heading. With the caret away every heading line shows its text only (`First heading`, `Second heading`, `Third`) with the heading line classes, the `#hashtag` line is untouched; with the caret on line 1 it shows `# First heading`. Screenshot taken.
- **Not checked:** headings inside lists and block quotes (lists and quotes arrive in T3), a heading while an IME composition is active, and how it looks in the light theme. The text is monospace; the preview does not change the editor font, which is outside every Phase 3 claim.
- **The Vite server I started is still running.** I stopped the background task, but its `node` process survived and an attempt to stop it by process id was refused, so I left it. The next tasks need it for the browser checks anyway; it must be stopped before the startup measurement in P3-T6.

## P3-T2: Emphasis and inline code

- **The parser is now GFM, in one place.** `src/editor/markdownSupport.ts` is `markdown({ base: markdownLanguage })`, used by the app and by the test helper. The default `markdown()` is CommonMark, which has no `Strikethrough` node (the advisor flagged it, and `tests/editor/markdownSupport.test.ts` shows `~~x~~` parses with GFM and not without), and Phase 4 needs GFM tables and task lists anyway. **Effect on speed, not measured here:** the P0 typing numbers were taken with the CommonMark parser, and GFM adds block and inline parsers. P3-T6 measures typing, open and tab switch with the final parser and layer, so nothing is claimed about it until then.
- **What each element does.** Bold, italic, strikethrough and inline code get a style over the whole element (markers included, which are then hidden), and each marker child is hidden unless the selection touches the element, edges included. Nested elements reveal on their own: the caret in `*italic*` inside `**bold ...**` shows both pairs, and the caret in the bold text outside the italic shows only the bold pair. Inline code gets the mono font, the code color and the code background from tokens; no new tokens.
- **Left as the parser decides:** intraword underscores (`snake_case_word` is not italic), unclosed markers, escaped markers, a single tilde. These are tested as "stays untouched" so a parser change that starts matching them fails.
- **Mutation proofs (the code broken on purpose, then restored):** wrong strikethrough mark name: 2 tests fail. Caret ignored (always hide): 10. Italic node left out: 4. Inline code mark left out: 4. The restored code passes all 104 editor tests.
- **Checked in Claude in Chrome (`pnpm dev`):** italic, bold, strikethrough and code render in one line; the caret in `**bold**` showed that pair only, on a word showed none, in `` `code` `` showed its backticks; the document text was identical after every move. The heading underline from CodeMirror's default highlight style is gone.
- **Checked in the real window:** `inline.md` with the caret on the last line shows `Some italic, bold, strike and code in one line.` and `Nested bold with italic inside here.` with the right styles (screenshot); the caret in the first of two bold spans reveals that span only; in `` `code` `` its backticks; in the nested italic both pairs.
- **A trap in my own driver.** The first real-window runs opened the file through `import('/src/documents/store.ts')`, but the Vite server had seen edits since the app loaded, so the app imported the store with a `?t=` stamp and my import made a second copy with its own document map. The tab existed, its document did not, and the pane stayed blank. Not a product bug (the same trap as in P2-T5). The driver now takes the module URL from the app's own resource entries.
- **Not checked:** emphasis inside link text (T3), inside block quotes and list items (T3), intraword emphasis next to CJK text, and the light theme. Typing speed with GFM and the layer is P3-T6.

## P3-T3: Links, lists, blockquotes and rules

- **Links.** `Link` nodes (inline, reference and shortcut) get the link style over the whole node. Away from the caret the opening `[` and everything from the closing `]` to the end of the node are hidden, so `[text](url "title")`, `[text][ref]` and `[text]` all read as `text`. The caret anywhere in the node, edges included, shows all of it. Hidden ranges are cut at line breaks (`hideLines`), so a title that wraps never produces a hidden range across lines. A link with no text (`[](url)`) is left raw: hiding it leaves nothing to see or to put the caret on, the same call as the bare `#`.
- **Autolinks and bare URLs.** `<http://x>` hides its angle brackets and styles the address; a bare `http://x` is only styled. A `URL` node inside a link, image, autolink or reference definition is not styled on its own (`addressed` set), so nothing is marked twice.
- **Left alone on purpose:** images (`![alt](src)`, no claim in this phase covers them) and reference definitions (`[ref]: url`), which are the one place the address is the content.
- **Lists.** Markers (`-`, `*`, `+`, `1.`, `2)`) get a marker style and are never hidden, so nothing can stick on them. I did not add a hanging indent or a `cm-md-li` line class: nothing in ISC-54 needs it, and padding on list lines is the kind of change that has to be re-checked against the arrow-key walk in T4.
- **Blockquotes.** Every line of a quote gets one line style (a nested quote and a lazy continuation line included, tracked by line start so a line is never styled twice). Each `>` and the blank after it hides unless the caret is on that line; a marker with nothing after it stays, so an empty quoted line keeps a character to land on. The style is a left bar plus padding on the line (not a margin, per the CodeMirror gotcha). Nested quotes look the same as outer ones.
- **Rules.** `HorizontalRule` gets a line style with a bottom border and its text hides unless the caret is on that line. The border sits at the bottom of the line, so with the text shown it is a rule under `---` rather than through it.
- **Mutation proofs (the code broken on purpose, then restored):** link ignores the caret: 3 tests fail. One hidden range across lines: 1. Empty link hidden: 1. URL rule widened to links: 2. Autolink brackets kept: 1. List marker style removed: 2. Quote lines styled twice: 1. Empty quote marker hidden: 1. Quote marker ignores the caret: 2. Blank after the marker left visible: 4. Rule never hides: 2. Rule ignores the caret: 2. All 12 are caught; the restored code passes all 540 tests.
- **Checked in the real window** (`blocks.md`): with the caret on the last line the link reads `docs`, the autolink reads `http://auto.example.com`, list markers are dim and the text is unchanged, the quote has its bar and no `>`, the rule is a line across the pane. With the caret in the link the full `[docs](http://example.com/docs "Docs")` shows; in the nested quote only that line shows `> > nested quote`; on the rule line `---` shows. The document length was the same after every move. Screenshots taken.
- **Not checked:** the light theme, an image next to a link, a heading or a code block inside a quote or list, a link split by an IME composition, and mouse clicks on hidden syntax (T4).

## P3-T4: Reveal, atomic ranges and the caret walk

- **Deviation: no transaction filter.** The plan says hidden markers get atomic ranges "with a transaction filter so selections can't land inside them". I did not build the filter. Every range the layer hides sits inside the span whose touch reveals it (the node for emphasis, code and links; the line for heading marks, quote marks and rules), and a caret in or on the edge of a span always touches it. So a selection can never end strictly inside syntax that is hidden, and a filter that checks for it could never fire, which means no test could prove it works. What exists instead is the check itself: `caretWalk.test.ts` asserts after every caret step that no selection end is strictly inside a hide item, and breaking any reveal rule fails it. **When the filter comes back:** the first replacement that stays hidden while touched, such as the Phase 4 frontmatter pill or the table and image widgets. Then a caret can legitimately sit next to something it must not enter, and `atomicRanges` alone does not stop programmatic selection from landing in it (the `AGENTS.md` note).
- **Atomic ranges are in, from hide items only.** The plugin keeps a second set holding only the hidden ranges. Handing `atomicRanges` the decoration set would make every mark (a whole bold word, a whole link) atomic and the caret would jump over them; a test fails on exactly that mutation. `livePreview({ atomic: false })` turns it off for the walk.
- **The walks run without atomic ranges.** With them on, the caret jumps over a position the reveal rule should have shown, which hid one of my own mutations (a quote marker that checked the wrong line). Without them the walk tests the rule itself. The last tests walk a document of every element with them on and compare the heads to the walk with them off: identical, so they change nothing today.
- **How the walk checks, and what it covers.** A real jsdom view with the real plugin, driven by CodeMirror's own commands (`cursorCharRight/Left`, `cursorGroupRight/Left`, `selectCharRight`). jsdom has no `Range.getClientRects`, so the test polyfills it. Each step asserts the head moved in the right direction, that it is inside a scanned viewport (a walk over undecorated text would prove nothing), and that no selection end is inside a hide item. Coverage: the eight files in `tests/fixtures`, decoded as the app shows them (UTF-16 and Latin-1 decoded, BOM stripped, every line ending `\n`), and one document of every element and odd shape (empty link, bare `>`, `- - -`, a quote around a heading, a link title that wraps). **The seven generated files (1 to 10 MB) are not walked whole**: that is millions of positions. Each gets two seeded windows of about 4000 characters, cut at paragraph starts. A window shows the layer the same text the whole file would, since it works from the viewport. They are walked with the layer forced on (`createState` with it), even though the app shows files above 3 MiB as plain source.
- **What the walk cannot see.** A hide only one character wide (an autolink's `<` and `>`) can never contain a caret strictly inside it, so the walk cannot tell if its reveal rule breaks. A test in `links.test.ts` covers that instead; I found it missing by mutation and added it.
- **Mutation proofs:** `reveal.test.ts` (touch reveals the line: 10 tests fail; reveals the paragraph: 10; edges excluded: 1; never revealed: 9). `caretWalk.test.ts`: emphasis reveal span two shorter at the start, heading, quote, link and rule each fail the walk; atomic set with the marks fails the with-and-without comparison. The autolink reveal broken fails 1 test in `links.test.ts` and none in the walk, as above.
- **ISC-58, `pnpm perf reveal`.** On the 1 MB fixture, the caret moves 80 times each way between a bold span in a 392-character formatted line and a line six below, in a view that shows both. Work per move is the dispatch plus the next frame's style, layout and paint, as in the typing scenario. Release app, Windows 11, Ryzen 7 8840HS, WebView2 157: leaving p95 3.7 ms (update 2.0, frame 1.7), max 4.6 ms; entering p95 3.9 ms. After every move the scenario reads the line's own DOM and throws if leaving did not hide the span's markers or entering did not show them. **How it went wrong first:** my first check compared the whole raw line with the page, but entering a span reveals only that span (the line's links and code stay hidden), so every entering move counted as wrong (90 per run). The harness did not fail the run, because timed scenarios ignore `checkFailed` (only `check` specs read it); a second run with `--skip-build` then ran the old bundle inside the exe and proved nothing. The scenario now throws, and the final numbers are from a rebuild with 0 wrong states in all five runs. Note for later: `pnpm perf` needs the build whenever frontend code changes.
- **ISC-60 and the mouse, in the real window.** ArrowDown and ArrowUp with trusted key events walked a 37-line document of every element, `lf.md` (368 lines, 469 presses because lines wrap) and a 17-line one: no skipped line, no stuck press, text unchanged. The same in Claude in Chrome on `pnpm dev` over 33 lines. Real mouse events: a click in the middle of a rendered bold word puts the caret in that word and reveals that span only; a click right of a line goes to its end; a click on the hidden closing markers puts the caret at or inside that span. A drag from inside the first span across the second: the anchor is where the press landed, and with the pointer held still for ten more mouse moves the head stays on one position (107 each time) and does not move on release. The head ends two characters away from the pointer's original text position, because revealing the second span after the last move shifts the text under the pointer; that is how reveal-on-touch works and it settles, so no feedback loop.
- **Not checked:** vertical moves in the plain-source path (no layer there), drag selection that starts on a hidden marker (the press lands on the nearest edge), touch input, IME composition inside a revealed span, and the light theme.

## P3-T5: Source toggle and raw copy

- **The mode belongs to the pane, and `PaneEditor` owns it.** The pane's view logic moved out of `EditorHost.vue` into `src/workbench/paneEditor.ts`, so a test can drive the real thing without a Vue test library (the project has none). The raw flag lives in `src/workbench/rawMode.ts` (a reactive set of pane ids, session only); `PaneView` passes it down as a prop. `PaneEditor.show()` re-applies the pane's mode every time a tab is shown, so a tab last shown raw in another pane comes up in the mode of the pane it is dragged into.
- **The switch is a Compartment holding the same constant extension instances** (`src/editor/previewMode.ts`), so toggling reconfigures cheaply. It goes through `follower.reconfigure`, not the view, so the document sees a setting and not an edit. A plain-source tab has no compartment and `previewEffect` returns null, so the toggle does nothing there.
- **Command `view.toggleRawSource`, Ctrl+E** (Cmd+E on a Mac), enabled when there is a tab, with a menu entry right after Toggle Sidebar. I picked Ctrl+E because nothing else binds it; change it if you want another key.
- **Copy gets the endings back from the document.** The editor text holds `\n` only, so a plain copy of a CRLF file would hand over LF. The follower now reaches the master's endings through `FollowerLink.endings()`, and `src/editor/sourceCopy.ts` is a `clipboardOutputFilter` that rebuilds each copied piece with `joinWithEndings(piece, endings, firstBreak)` (new third parameter: index of the piece's first break in the whole document). It replicates CodeMirror's choice of pieces (non-empty ranges, else the caret's lines) and leaves the text alone if it does not match, so another filter's output is never overwritten. Cut and drag-out go through the same filter.
- **Hidden syntax needs no special handling to be copied.** Live preview only hides text, so the selection still spans it; the test proves it byte for byte on three fixtures.
- **Found by the real window, not by tests:** nothing. The first run of the driver failed on its own expectation (a double UTF-16 decode) and then on state left by the first run (three panes); neither was an app fault. The clipboard bytes were right on the first run.
- **Not checked:** copy inside a pane in a large (plain-source) file (same filter, no layer), drag-out of a selection to another application, paste behaviour (a paste of mixed endings is normalized by the existing load path, not changed here), and the menu entry in the native macOS menu.

## P3-T6: Typing and startup targets with preview on

Release build, Windows 11, Ryzen 7 8840HS, WebView2 157, commit `c98e4d0`, 5 runs after 2 warm-ups unless noted. Every speed gate passes with the real live-preview layer.

| Claim | Result | Limit |
|---|---|---|
| ISC-4 startup | 515 ms (514 to 529) | 1000 ms |
| ISC-5 open 1 MB | 22.5 ms | 100 ms |
| ISC-6 tab switch p95 | 16.1 ms | 50 ms |
| ISC-7 typing p95, 1 MB | 5.8 ms (6.7 ms with trusted keys) | 16 ms |
| ISC-58 reveal p95 | 4.0 ms | 16 ms |
| crash-restore | 5 tabs and 3 unsaved buffers back exactly, 104 ms | none |

- **Startup is 515 ms, 10 ms over Phase 2 and 40 over the bare shell.** The time is WebView2 starting (298 ms from Rust main to page start); the app itself is 118 ms to mount and 44 ms to an editor.
- **Typing grew about 0.8 ms from Phase 0** (5.0 to 5.8 ms p95), the cost of the real layer and the GFM parser over the throwaway decorations. The T2 worry that the GFM parser would raise typing cost is answered: it did, by well under a millisecond.
- **The 3 MiB cutoff stays.** Typing at 2, 3, 5 and 10 MB: p95 6.0, 8.2, 12.6, 16.5 ms; p99 6.9, 9.0, 13.5, 17.4. The 3 MB fixture is 406 bytes over the cutoff, so it stands for the largest file that keeps the parser: p99 9.0 against 16. 10 MB is over and not repeatable, which is the reason files that big open as plain source.
- **ISC-63 missed its 20 percent limit with the full layer, then moved to 35 on your call.** Late in the file the scan takes about 48 microseconds at 10 MB against 40 at 1 MB. Six runs: ratios 1.28, 1.27, 1.20, 1.20, 1.16 and one noisy 1.05. The whole view update stays level (0.42 against 0.41 ms) and the work is identical in both files, so I read it as the cost of finding a place in a bigger syntax tree, not a scan that grows with the file. I did not profile it. With 35 percent: worst deviation 14.7 percent, control 8.5 times.
- **`journal-cost`** (not tied to preview): a 1 MB snapshot builds in 4.9 ms and writes in 25.7 ms with a worst frame gap of 16.8 ms, one frame; at 4 MB the gap is 27.9 ms. The journal interval is unchanged.
- **`pnpm perf all` also runs `lab-drag`**, a P5 spike that asks a person to answer 12 questions. It recorded all "yes" in this run and I did not answer it; it is not evidence for anything in Phase 3, and `all` stopping on a person is worth fixing when P5 starts.
- **The first `pnpm perf all` was killed by the system for low memory** during the Rust build and measured nothing; it was rerun after other programs were closed. CPU idle before launch was 73 to 91 percent, below the harness's 85 percent warning in a few runs of reveal, tab-switch and typing; those runs still repeat within 10 percent.
- **Not checked:** startup on a fresh WebView2 profile (the data directory is fresh each run but the WebView2 profile is the warm one), the light theme, and a file of exactly 3 MiB (the 3 MB fixture is 3,146,134 bytes, 406 over the cutoff, so it is the right size to stand for the largest parsed file).
